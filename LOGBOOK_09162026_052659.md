# Logbook — P7 fabricated-passage bug: root-caused and fixed, real inference verified

**2026-09-16.** Follow-up to the 2026-09-15 P7 batch re-run (`LOGBOOK_09152026_092024.md`), which
fixed one citation bug but surfaced structural trace-validity actually dropping (77/100 valid vs.
the old buggy run's 468/483) once measured on a full 20-query batch instead of 2 unit tests.

## Root cause

Once the model finishes a short real answer with token budget left over, it can keep generating --
and having seen `build_prompt`'s own passage-block format (`"[chunk_id] (from doc_id):\ntext"`,
joined with blank lines between passages) repeated several times in its own context, it
pattern-completes by fabricating entire additional fake "passages" in that exact format: invented,
plausible-sounding doc_ids (e.g. `https_en_wikipedia_org_wiki_Curse_of_dimensionality_86754123`) with
fabricated but topically-relevant content that was never actually retrieved. One real example
produced four such fake passages in a row. This is a distinct failure mode from the 2026-09-15 fix
(the model echoing the literal instructional word `chunk_id`) -- not a recurrence of that bug.

Two smaller, separate patterns also present in the same batch, not addressed here: the model using
square brackets for plain emphasis/terminology (`[bag of words]`), and raw Wikipedia markup noise
(footnote markers, table syntax) surviving in the crawled corpus text and occasionally being quoted
verbatim. Both are real but lower-severity than the fabrication pattern and out of scope for this fix.

## Fix

`answer/model.py`'s `generate()`:
- Added `"\nAnswer:"` / `"\n\nAnswer:"` to the `stop` list -- catches the model restarting an entire
  fake new Q&A turn (also observed in the batch).
- Added `"] (from "` to `stop` -- the exact phrase only `build_prompt`'s own passage block ever uses;
  no legitimate citation the model writes is ever followed by it, verified by checking every valid
  citation's surrounding context in the 2026-09-15 batch (several legitimately start a fresh
  paragraph after `\n\n`, so a naive "stop at any line-starting bracket" rule was rejected -- it would
  have cut off correct answers).
- New `answer/repetition.truncate_on_fabricated_passage()` -- post-hoc cleanup for the one citation
  that's already been emitted by the time `"] (from "` becomes visible (the stop string can only match
  after its own preceding bracket exists). Same pattern and file as the existing
  `truncate_on_repeat()` guard from the 2026-09-08 batch.
- 8 unit tests pass (2 new, built directly from real captured fabrication text from the 2026-09-15
  batch -- not synthetic).

## Verification

Real (non-mocked) end-to-end re-run of the single worst-offending query from the 2026-09-15 batch
("layered proximity graph structure for nearest neighbor search", which previously produced 4
fabricated citations):
```
citations_found: ['doc26_hnsw::0', 'doc09_vector_embeddings::0']
valid_citations:  ['doc26_hnsw::0', 'doc09_vector_embeddings::0']
invalid_citations: []
```
Clean. The real, correct portion of the answer is byte-identical to before up through the point where
fabrication used to start. **One thing not fully pinned down, stated plainly rather than overclaimed**:
the raw output still contains an incomplete fragment of the same fabrication attempt
(`...Curse_of_dimensionality_86754123::9`, no closing bracket) -- so the model still *attempts* to
fabricate, it just doesn't complete far enough to become an extractable, invalid citation this run.
`answer_text` was only ~950 chars (~200 tokens, well under the 512-token ceiling), so `max_tokens`
didn't cause the cutoff either. This run isn't a clean single-variable comparison against the
2026-09-15 failure -- the prompt wording also changed between them (the earlier citation-example fix)
-- so I can't cleanly attribute this specific cutoff to the new stop sequences vs. the updated prompt
vs. the model's own stopping behavior. The *outcome* (no invalid citation exposed, correct content
intact) is verified real; the exact internal mechanism for this one run is not fully explained.
