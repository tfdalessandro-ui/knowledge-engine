# Logbook — Instance sync: original ↔ instances, built and verified live

**2026-09-16 (23:35 UTC).** User requirement, stated during the OSE rename: *instances stay in sync with the
scaffolding and logic. As the original evolves, its changes flow to the instances. If an instance evolves
differently and improves, the best version becomes the source.* Built gradually, with a regression check per step.

## Why it was needed (measured, not assumed)

The Sensalis clone was 20+ commits behind the original, and 4 of its scripts had been hand-edited to differ only in
service name and port. Those per-copy edits are what made its `auto_tune.py` restart and validate the *original*
engine (`LOGBOOK_09162026_233000.md`). With that hardcoding in place, no automatic sync was possible.

## Design

- **Instance = branch.** `instance/<name>` is OSE `main` plus instance-owned paths only (`OSE_INSTANCE_PATHS`).
  Identity (service, port, smoke queries, branch) lives in a committed `instance.env` read by `config.Settings`. It stays
  out of `.env`, which `auto_tune.py` rewrites wholesale, so a tuning deploy would wipe it. Shared code never hardcodes identity.
- **main → instance:** `scripts/sync_instance.py` merges `origin/main`, restarts the instance, and compares every test's
  outcome and the top 5 of each pinned smoke query against the pre-merge state. On any regression it hard-resets to the pre-merge
  commit and restarts. It runs daily at 05:15 UTC through `ose-sync@<dir>.timer`. The instance's `origin` is GitHub (fetch-only), so
  syncing doesn't depend on `~/work/ose` being pulled first.
- **instance → main:** `scripts/promote_check.py` applies the instance's shared-path changes to a throwaway worktree of
  `origin/main`, then runs tests plus `eval.run --index hybrid` on both it and an unmodified worktree. PROMOTE = applies cleanly,
  no test newly fails, nDCG@10 not lower. "Best becomes the source" is measured on OSE's own judgment set, the only real
  ground truth available (the Sensalis instance has none yet).
- Instance branches are never pushed to GitHub, because they contain real Sensalis pricing data.

## Limits, stated plainly

- **Promotion is gated, not unattended.** The node has no GitHub push credentials, so a PROMOTE patch must be committed to
  `main` from the laptop. Fully unattended promotion would need a push-capable deploy key on the node. That's an owner decision.
- **Forward sync treats any change to a pinned ranking as a regression** and rolls back. A genuine ranking improvement on `main`
  therefore needs a human-reviewed rerun with `--accept-ranking-changes`. This is conservative on purpose: the instance has no
  judgments to tell an improvement from a regression.
- Promotion compares on OSE's judgment set only. Something that helps Sensalis parts search but not search-tech queries would
  still be promoted only if it doesn't lower OSE's nDCG@10. Real Sensalis judgments would allow a second, instance-side gate.
