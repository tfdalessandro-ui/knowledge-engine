## Round-2 GA + cross-validation, ~21 held-out queries per fold

`ga_tune_hybrid_cv2.py` (deleted after use, same discipline as every
prior one-off script this investigation produced). Key implementation
difference from round 1, needed to make a denser search over 106 queries
practical: precomputed each query's BM25 and vector candidate lists
(up to fanout=150) ONCE, cached, and reused across every genome/fold --
only RRF fusion (cheap, pure Python) differs per genome, since
`chunk_fanout` just truncates the cached lists and `rrf_k` only changes
the fusion formula. **Sanity-checked this optimization before trusting
it**: compared its output against the real, unmodified `HybridIndex.search()`
on a 15-query subset at the default (60,100) -- exact match
(0.910460647... both ways) before running anything else on it.

5-fold CV, ~21 held-out queries per fold (vs round 1's ~6):

```
Fold  GA genome (train)  train rel.   held-out: GA genome   held-out: default(60,100)
0     (1, 20)             -0.01%       +2.64%                -2.52%
1     (1, 85)             +0.08%       +2.45%                +3.43%
2     (1, 22)             -0.14%       +3.37%                +3.80%
3     (1, 77)             +0.97%       -1.06%                -4.04%
4     (1, 52)             +1.86%       -4.75%                -8.25%

Average TRAIN rel_improvement (GA, in-sample):        +0.55%
Average HELD-OUT rel_improvement (GA genome):          +0.53%
Average HELD-OUT rel_improvement (default 60,100):     -1.51%
Genomes selected per fold: [(1,20) (1,85) (1,22) (1,77) (1,52)]

Full-set (non-CV) reference: BM25=0.9017, GA best (1,62)=0.9067 (+0.55%),
default (60,100)=0.8878 (-1.54%)
```

**This is the opposite signature from round 1, and that contrast is the
actual evidence, not just the averages in isolation:**
1. **Stable winner across all 5 folds**: `rrf_k=1` every single time.
   Round 1's winners were scattered (`(61,30) (120,20) (57,129) (177,39)
   (1,52)`) with no agreement. `chunk_fanout` stayed noisy here too
   (20-85) -- it's `rrf_k` specifically that's the real, stable lever,
   not fanout.
2. **The GA's held-out average genuinely beats the default's held-out
   average** (+0.53% vs -1.51%), the opposite of round 1 where the GA's
   held-out average (-2.03%) was WORSE than the default's (-1.31%) --
   the textbook overfitting tell. Here there's no such tell.

**Conclusion: this is real, validated signal, confirmed by having enough
held-out data to actually distinguish signal from noise** -- something
round 1's ~6-queries-per-fold literally could not do reliably, exactly as
flagged as an open question in the prior two logbook entries.

## Deployed

User confirmed: deploy `rrf_k=1` to the live service.

**Changed, in order:**
1. `src/eval/hybrid_index.py` -- `HybridIndex.__init__`'s own class
   defaults changed from `(chunk_fanout=100, rrf_k=60)` to
   `(chunk_fanout=62, rrf_k=1)`, with an inline comment citing this
   investigation so a future reader isn't left guessing why these
   specific, unusual-looking numbers are the defaults.
2. `src/config/__init__.py` -- added `hybrid_rrf_k: int = 1` and
   `hybrid_chunk_fanout: int = 62` to `Settings`, env-configurable via
   `KE_HYBRID_RRF_K` / `KE_HYBRID_CHUNK_FANOUT` -- matches this project's
   own stated convention ("nothing hardcodes a path, host, or port")
   rather than leaving the tuned values only inside the class signature.
3. `src/api/main.py` -- `_get_index()` now passes
   `chunk_fanout=_settings.hybrid_chunk_fanout, rrf_k=_settings.hybrid_rrf_k`
   explicitly into `HybridIndex(...)`, so the live service is
   config-driven, not just relying on the class default silently.
4. `src/eval/run.py` -- the `--index hybrid` CLI path gets the same
   explicit settings wiring, so `eval.run --index hybrid` and the live
   API always measure/serve the same configuration going forward.

**Verified before touching the live service:**
- All four changed files `py_compile` clean.
- Full `tests/eval/` + `tests/api/` suite re-run: **30 passed, 1 xfailed**
  (the P2 exit-criterion test itself, still short of +5%, expected),
  **0 regressions** -- `tests/api/test_main.py`'s 5 tests specifically
  confirm the new settings wiring into the live API code path works.

**Still NOT meeting the +5% exit criterion.** `xfail(strict=True)` stays
on `tests/eval/test_hybrid_vs_bm25.py`, correctly -- this is progress, not
a pass, and is reported as exactly that in the test's reason string,
README, and here. What changed today is real and deployed: the live
service now serves a genuinely better-than-BM25-only hybrid ranking,
confirmed two independent ways (cross-validated held-out testing before
deploy, live verification after), rather than continuing to serve a
configuration already known to underperform BM25-only.

**What would still be needed to close the remaining ~4.6 points to +5%**,
not attempted in this entry: growing the judgment set further isn't
promising on its own (already shown twice not to be the primary lever);
a finer-grained parameter search around the `rrf_k=1` region (e.g. also
trying non-integer-equivalent weighting schemes, or a proper weighted
fusion instead of plain RRF) is the more likely next avenue if this is
pursued further.
