# Logbook — OSE rename: Sensalis clone → `ose_sensalis` / `ose-sensalis.service`

**2026-09-16 (23:30 UTC).** Continues the gradual OSE rename. Each step had its own regression check.

## Findings (all real, all found before or while renaming)

1. **My own earlier rename had broken the clone for its next restart.** The clone's `.venv` was a copy of the original's, and its
   62 `.venv/bin/*` shebangs plus `pyvenv.cfg` still pointed at `/home/sensalis/work/knowledge_engine/.venv`, which
   stopped existing when that folder became `~/work/ose`. The clone looked healthy only because its process had been
   running since 15 Sep. A restart would have failed with `203/EXEC`. It also means the clone had been running on the **original's** Python
   packages all along, not its own copy (identical in this case: 323 entries, same size, so no behavior change).
2. **None of the Sensalis pilot work was ever committed** on either copy: the 1500-document corpus, `data/sensalis_raw/sample.csv`,
   `ingest_sensalis_pricing.py`, `bench_vs_scraper.py`, and the weighted-fusion wiring. It was the same loss risk that lost
   `research/`, `discovery/` and `adaptive_alpha.py` in the 14 Sep migration. The laptop and node copies had identical content
   once line endings were normalized, except `bench_vs_scraper.py`, which existed only on the laptop.
3. **The clone's scripts were aimed at the original engine**, not only `auto_tune.py`'s service name (TODO item 11):
   `auto_tune.py` also health-checked and query-checked `:8000`, so a clone deploy would have restarted the original engine
   and validated against it. `comparative_benchmark.py`, `comparative_benchmark_speed.py` and `status_recheck.py` also
   targeted `:8000` / `knowledge-engine.service`.
4. **The clone shares production Memgraph (`:7687`) and Postgres (`:5433`) with the original.** A KG extraction run in the clone
   would write Sensalis entities into the original's graph. Not fixed yet; nothing schedules one. (The clone's KG *tests*
   use the separate test instance on `:7688`; after running them, the original's KG still reads 215 entities / 9 relations.)
5. **The clone's judgment set is still the original's search-tech set**, so it doesn't match the Sensalis corpus. Any eval
   or auto-tune run on the clone would therefore tune against the wrong ground truth. That's why 12 KG tests fail on the clone
   (they expect entities like bm25, hetzner and fastapi), which was pre-existing and expected. Don't schedule auto-tune on the clone until it has Sensalis judgments.
6. The clone's git remote pointed at the old `~/work/knowledge_engine` path. It now points at `~/work/ose` (fetch verified).
