## Issue 1 — the unexplained `run_discovery()` bypass: root-caused (not just fixed blind)

**Investigation** (cron, other users' sessions, `journalctl`, leftover
scripts, live processes importing `discovery.pipeline`) found nothing
conclusive on its own -- but **fixing the fix itself revealed the real
cause**: adding self-logging and then running `pytest tests/api/` to
verify it showed `caller="api:/search"`, `argv` containing the literal
`pytest ... tests/api/` command line, for query `"alpha apples"`.

**Real root cause**: `tests/api/test_main.py`'s fixture builds a tiny
2-document test corpus (`alpha.txt` "about apples and orchards",
`beta.txt` "about bicycles"). BM25 scores on a 2-doc corpus are
legitimately much lower than on the real 47-doc corpus
`MIN_MEANINGFUL_BM25_SCORE=5.0` was calibrated against -- low enough that
even a genuine match falsely tripped `is_sparse()`, firing **real, live
web fetches against the real SearXNG/internet as a side effect of running
this project's own unit tests.** Every time I (or anyone) ran
`pytest tests/api/`, it silently discovered and indexed real e-commerce
apple-selling pages into production data. This is what actually happened
-- not an unattributed bypass, but a test-isolation bug I had already
triggered myself, repeatedly, without realizing it.

**Fix #1 (the one the plan asked for): self-logging.**
`ProvenanceStore` gained an `invocations` table and `log_invocation()`;
`run_discovery(query, settings, caller="unknown")` logs itself as its
very first action, before web_search/robots/fetch can even start.
`api/main.py` passes `caller="api:/search"`. Proven live:
```
$ .venv/bin/python -c "... store.log_invocation('proof-of-fix direct test call', caller='manual-verification-2026-09-06') ..."
logged invocation_id: 4
$ sqlite3 data/discovery_provenance.db 'SELECT * FROM invocations;'
1|alpha apples|api:/search|2389609|.../pytest/__main__.py -q tests/discovery/ tests/api/ -v|...
2|alpha apples|api:/search|2389609|...same pytest run...|...
3|alpha apples|api:/search|2389609|...same pytest run...|...
4|proof-of-fix direct test call|manual-verification-2026-09-06|2390108|-c|...
```

**Fix #2 (the actual bug, once found): test isolation.** Added
`discovery_enabled: bool` to `Settings` (NOT `discovery_sparse_threshold
=0` -- caught live before deploying that: `is_sparse([], threshold=0)` is
vacuously `True`, since "0 matches in an empty top-slice" == "0 real
matches", which would make EVERY query trigger discovery, the opposite of
disabling it). `api/main.py`'s check became `_settings.discovery_enabled
and is_sparse(...)`. `tests/api/test_main.py`'s fixture sets
`discovery_enabled=False`. New regression test
`test_discovery_never_fires_from_this_test_suite` proves it. Verified:
```
invocation count before test run: 4
$ pytest tests/api/ tests/discovery/ -v -> 15 passed
invocation count after test run: 4   (unchanged)
```

**Cleanup**: removed the 8 accidentally-indexed apple-commerce documents
(files, `discovered_registry.db`/index entries via a legitimate
`run_ingest` stale-cleanup pass, `provenance` rows) -- kept the
`invocations` audit rows, since those ARE the point. After cleanup:
`data/discovered/` = 3 files (the real zebra-migration demo only),
`discovered_registry.db` = 3, matching.

## Issue 2 — crawler now has a real TTL/re-fetch mechanism

`CrawlState.already_crawled()` (skip-forever) replaced with
`needs_fetch(url, ttl_days)` (eligible for re-fetch once the last fetch
is `>= ttl_days` old; `DEFAULT_TTL_DAYS = 1.0`, matching the timer's own
daily cadence). `content_hash` column added (schema-migrated for the
existing DB via `ALTER TABLE`). On a URL past its TTL: re-fetch, hash the
new content, compare against the stored hash -- unchanged content just
bumps `fetched_at` (`rechecked_unchanged`); changed content overwrites
the file and is reported separately (`rechecked_changed`), which then
flows into `ingest.pipeline`'s own already-working content-hash update
detection.

**Real run, today, live**:
```
$ PYTHONPATH=src .venv/bin/python -m crawl.pipeline
fetched=0 rechecked_unchanged=0 rechecked_changed=12 skipped_duplicate=0 skipped_robots_disallowed=0 errors=0
elapsed=22.2s budget=60s -> WITHIN BUDGET
ingest: scanned=12 added=0 updated=10 unchanged=2
```
All 12 URLs (last fetched 2026-09-03, now >1 day past TTL) were genuinely
re-fetched and re-hashed; all 12 had real content differences (plausible
-- these are live Wikipedia/sqlite.org/python.org pages, genuinely edited
over 3 days), 10 of which changed enough at the parsed-text level for
`ingest.pipeline` to register an update. `crawl_state.db` confirms fresh
`fetched_at` timestamps (2026-09-06) and populated `content_hash` values.

3 new tests added (`tests/crawl/test_crawl_pipeline.py`): TTL-not-expired
still skips (regression guard for the OLD correct behavior), TTL-expired
re-checks and correctly finds no change (new local-server fixture,
deterministic content), TTL-expired re-checks and correctly detects a
real change (new `local_server_with_mutable_content` fixture). All pass,
alongside the existing 27 crawl tests (30 total, `tests/crawl/`).
