## A real discrepancy, chased down rather than hand-waved

The nDCG@10/MRR I measured just now (0.8908/0.9107) don't exactly match
P1's original recorded baseline (0.8911/0.9286, `LOGBOOK_09022026_175124.md`).
recall@20 matched exactly (0.9048) both times, which narrowed it down: only
the metrics sensitive to *tie-break ordering among near-equal BM25 scores*
moved.

Root-caused by direct comparison rather than assumption: built two
independent fresh indices from the same corpus into throwaway directories
side by side —
```
fresh_A nDCG@10=0.8911 MRR=0.9286 recall@20=0.9048
fresh_B nDCG@10=0.8911 MRR=0.9286 recall@20=0.9048
live_current nDCG@10=0.8908 MRR=0.9107 recall@20=0.9048
```
Two independent fresh builds are byte-identical to each other and match the
*original* P1 baseline exactly. The currently-on-disk `data/tantivy_index/`
differs slightly — and the only thing that ever touched it differently from
a fresh build is my own edit→revert incremental-update test from earlier in
this same verification (delete_documents + re-add for `doc01_bm25`, twice).

**Conclusion: Tantivy's incremental delete+re-add path leaves BM25's
tie-break ordering slightly different from a fresh build, even when the
final indexed text converges back to byte-identical content.** This is not
a correctness bug — recall@20 (which doesn't care about ordering among
retrieved docs) was identical in all three cases, and nDCG@10 only moved by
0.0003. It's a real, minor reproducibility caveat: **an index that has been
incrementally updated is not guaranteed to score identically to a freshly
built index over the same final content**, most visible in MRR (which is
sensitive to a single rank-1 tie flipping).

**Why this matters going into P2:** P2's exit criterion is "hybrid beats
BM25-only by +5% nDCG@10." That comparison should be made against a
freshly-built BM25 baseline (or the two sides of the comparison should share
the same index-build history), not against whatever incrementally-mutated
index happens to be on disk — a ~0.03% nDCG@10 / ~2pp MRR drift from
incremental updates alone would otherwise be indistinguishable from a small
real improvement. Restored the on-disk index to the fresh-build state
(deleted and re-ran `ingest.pipeline` from scratch) before finishing this
verification, so P2 starts from the same state as `fresh_A`/`fresh_B`.
