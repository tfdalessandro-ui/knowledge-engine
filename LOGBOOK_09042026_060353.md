## What was built (real module, not an ad-hoc script this time)

`src/eval/weighted_fusion.py` -- min-max normalizes BM25 and vector
scores to [0,1] within each query's own candidate set (RRF deliberately
discards score magnitude and uses rank only; this keeps the magnitude
information), then combines as `alpha * norm_bm25 + (1-alpha) *
norm_vector`. A doc in only one side gets 0 for the missing side
(CombSum-style zero-fill). Unit-tested
(`tests/eval/test_weighted_fusion.py`, 7 tests: alpha=1/0 edge cases,
zero-fill inclusion, agreement-wins, all-tied normalization, empty
inputs, invalid-alpha validation) -- all pass. This is a real, permanent
addition to the codebase, unlike the disposable `ga_tune_*.py` scripts
from prior sessions.

## Fork points -- every tuning decision this session as a marked branch, not just a record

Per the user's explicit instruction: each parameter/methodology choice
below is a point where this investigation could have gone, or still
could go, a different direction from the exact same starting data. Noted
here so a future session can pick any of these up without re-deriving
the context.

1. **Fusion algorithm family.** Chosen: RRF (round 1) then weighted
   CombSum-style score fusion (round 2, deployed). NOT explored:
   CombMNZ (weight by how many source lists a doc appears in, on top of
   summed score -- rewards agreement more explicitly than plain CombSum),
   Borda count, or a learned fusion function (logistic regression / small
   MLP over [bm25_score, vector_score, other features] -- effectively a
   tiny version of the P3 LTR reranker this project already has
   infrastructure for, still blocked at 0/500 real interactions).
2. **Score normalization method.** Chosen: min-max within each query's
   own candidate set. NOT explored: z-score normalization (more standard
   in some IR fusion literature, less sensitive to outlier scores at the
   top of a list than min-max is), or a GLOBAL calibration fit once
   across the whole corpus/judgment set rather than per-query -- per-query
   min-max can behave oddly for a query with very few candidates or an
   unusually tight/wide score spread.
3. **Alpha: fixed global constant (0.535).** NOT explored: alpha as a
   function of query features (query length, whether it looks like an
   exact-phrase/keyword query vs. a conceptual one) -- this session's
   judgment set has enough query variety (106 queries, many explicitly
   literal vs. many explicitly conceptual, by design from the growth
   session) to potentially support this as a real experiment, not a
   guess.
4. **chunk_fanout: pragmatic mid-range pick (100), not a tuned
   optimum.** Confirmed twice that this parameter is close to flat across
   a wide range (35-276) for THIS corpus's small scale (341 chunks total)
   -- worth re-testing once/if the corpus grows meaningfully, since a much
   larger corpus might make fanout matter more (more real candidates to
   miss by cutting off too early).
5. **GA hyperparameters themselves** (population size, generations,
   mutation step, elite count) were picked pragmatically (12→16→20 pop,
   8→12→16 gen across the three GA runs this investigation ran) and
   never independently validated -- it's possible a different GA
   configuration converges faster or finds a better optimum; not tested,
   since the actual alpha/rrf_k findings converged quickly and
   consistently enough that GA-hyperparameter tuning didn't seem like the
   bottleneck.
6. **Judgment set: grown to 106 queries, but not restructured.** Every
   CV run this investigation did re-shuffles and re-folds the SAME 106
   queries fresh each time (`random.seed(7)` in each script, so folds are
   reproducible run-to-run, but there's no PERMANENT held-out set set
   aside across sessions). A fork not taken: carve out a fixed, permanent
   held-out slice of the judgment set (e.g. 20 queries, never used for
   tuning, only for final verification) so future tuning attempts can't
   even accidentally leak into what they're being validated against --
   more rigorous than fresh k-fold every time, at the cost of less data
   per fold.
7. **rrf_k=1's own degenerate-corner nature was flagged in round 1 but
   never separately investigated.** A fork not taken: understand WHY
   rrf_k=1 (and alpha~0.535, which similarly favors sharper distinctions
   over smooth blending) work better here -- is it specific to this
   corpus's small size, its keyword-heavy synthetic query style, or a
   more general property that would hold at a larger scale? Untested;
   would need a genuinely larger corpus to check, which is outside what
   this project can produce on its own without inventing content.
8. **The weighted-fusion candidate pool is still built from the SAME
   underlying `chunk_fanout`-limited BM25/vector searches as RRF used.**
   A fork not taken: decouple the two sides' fanout (e.g. a smaller BM25
   fanout since exact matches concentrate near the top, a larger vector
   fanout since semantic relevance decays more gradually) -- untested,
   the GA search space treated `chunk_fanout` as one shared knob for both
   sides throughout this whole investigation.

None of these are "next todos" -- they're explicitly marked as unexplored
branches from where this investigation currently stands, offered so a
future session (or this one, later) can pick one up deliberately rather
than rediscovering that it was even an option.
