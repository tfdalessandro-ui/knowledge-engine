# Logbook — P5: Enterprise Connectors & Access Control (ACL core + Git only)

**2026-09-03, ~08:08 CEST** (computed as `date -u -d "+2 hours"`, per the
tooling note in `LOGBOOK_09032026_000504.md`)

## Scope, per the roadmap artifact

P5 = "Enterprise connectors & access control" — a **hard gate**: no
enterprise source gets indexed before permission-aware retrieval exists to
gate it. Deliverable: SharePoint, OneDrive, Outlook, Teams, and Git
connectors, each tagging documents with source ACLs at ingest; retrieval
filters by the requesting user's permissions before ranking. Tech choice:
PostgreSQL (metadata store). Exit criterion: a permission-denial test suite
passes — user A cannot see user B's private files — before this reaches a
second user.

## Flagged before building anything: real credentials, not open-source tooling

Unlike every prior phase's tech choice (Docling, Tantivy, FAISS, LightGBM,
spaCy, Memgraph — all open-source, locally runnable), SharePoint/OneDrive/
Outlook/Teams connectors need a real Microsoft Graph API Azure AD app
registration and tenant access. This project has none. Building against
mocked/fake OAuth would produce something that *looks* connected without
being validated against anything real — a materially different kind of gap
than P3's "no real usage yet" (which was about data volume, not missing
infrastructure this project could never self-provision). Asked the user
before choosing a path. Answer: build the real, testable pieces — ACL core
+ Git connector (needs no OAuth) — and leave the four Microsoft connectors
explicitly not built, same pattern as P3's gated LTR training.

## What got built

- `src/access/acl_store.py` — `AclStore`, PostgreSQL-backed. Two tables:
  `documents` (doc_id, source, owner_user_id, is_public) and
  `document_acl` (doc_id, user_id grants). Authorization model, deliberately
  simple for a v1 gate: visible if public, OR owned, OR explicitly granted.
  No groups/roles yet — the exit criterion is proving cross-user leakage is
  impossible, not modeling a full enterprise permission system.
- `src/access/git_connector.py` — `ingest_git_repo()`: routes a local
  working directory through the SAME BM25 pipeline every other corpus
  document uses (`ingest.pipeline.run_ingest`), then registers each file's
  ACL from an explicit manifest (a real connector would derive this from a
  Git host's collaborator API; this takes the same shape of information as
  an explicit input instead, since there's no real tenant to query).
  **Default-deny:** a file not in the manifest gets registered locked down
  (no owner, not public) — indexing ahead of a known ACL is exactly the
  leakage risk this phase exists to prevent, so the safe direction to be
  wrong in is "nobody can see it yet."
- `src/access/permission_filter.py` — `PermissionAwareSearch`: wraps any
  existing index, over-fetches a larger candidate pool, filters by the
  user's authorized set, truncates to `k`. Documented as NOT a true
  index-level ACL push-down (out of scope for this gate) — a known,
  disclosed limitation (small authorized fraction of a large corpus could
  return fewer than `k` results).
- `src/access/connectors.py` — status registry: `git` CONNECTED, the other
  4 `NOT_CONFIGURED` with the reason stated, checkable via `access.status`
  — same honest-gate pattern as `ltr.status`.
- `data/enterprise_demo/` — a real (if small) demo dataset: one public
  policy doc, two users' private notes (each with a unique, searchable
  codename — "Project Nightingale" for Alice, "Project Kingfisher" for Bob
  — so leakage would be unambiguous if it happened), one doc explicitly
  shared from Alice to Bob ("Project Falcon"), plus `acl_manifest.json`.
- Tests: `tests/access/test_acl_store.py`, `test_git_connector.py`,
  `test_permission_filter.py`, `test_connectors.py` (pure Python, no infra),
  `test_permission_denial.py` (the exit criterion itself, 7 scenarios).

## Infrastructure: a new external service, handled carefully

Checking Docker port usage on sensalis-node before adding Postgres found
`log-postgres` already bound to `127.0.0.1:5432` (part of the unrelated
"logitude" workload found during P4). Started this project's own instance
on **5433** instead: `docker run -d --name postgres_ke -p
127.0.0.1:5433:5432 -e POSTGRES_PASSWORD=ke_dev_password -e
POSTGRES_DB=knowledge_engine --restart unless-stopped postgres:16-alpine`
— matching the node's `127.0.0.1`-only convention from the start this time
(learned from P4's Memgraph port-binding miss). `POSTGRES_PASSWORD` here is
a throwaway local dev credential for a loopback-only container, documented
explicitly as not a real secret.

**Deliberately did NOT migrate P1-P4's SQLite stores to Postgres.** The
roadmap's tech-choice line reads "PostgreSQL (metadata store, replacing
SQLite at this scale)" — read as "introduce Postgres for what P5 adds," not
"migrate `registry.db`/`vectors.db`/`query_log.db`/`merge_review.db`,"
since the permission-denial exit criterion doesn't touch any of those.
Migrating everything would be a much larger, separate undertaking outside
this gate's actual scope — flagging the interpretation here rather than
silently picking the narrower reading without saying so.

**Kept the enterprise-demo content in its own index**
(`data/enterprise_tantivy_index/`/`data/enterprise_registry.db`), separate
from `data/tantivy_index/`/`data/registry.db` — realized before running
anything that reusing the main index would mix ungoverned enterprise
content into the exact index the P1/P2 baseline numbers (nDCG@10=0.8912
etc.) were recorded against, silently invalidating those documented
numbers for an unrelated reason.

## A real bug caught by running the connector for real, not by inspection

First live run of `access.ingest_git` against `data/enterprise_demo/`
printed `documents_ingested=5` against 4 real content files — the extra one
was `acl_manifest.json` itself, sitting inside the same directory it
describes, getting scanned by the generic file walk (it's valid JSON, and
`ingest.parsers` handles `.json`) and locked down as an ordinary document.
Harmless in outcome (default-deny meant it was never visible to anyone),
but not the intent, and a real rough edge a user would hit immediately.
Fixed: `ingest_git_repo()` now takes an explicit `manifest_path` and
excludes it from ACL registration. **Residual, accepted limitation,
disclosed rather than silently left implicit:** the manifest's raw text
still gets content-indexed in Tantivy (the underlying `run_ingest` call
doesn't know to exclude it), just never ACL-registered — functionally safe
(it can never be authorized for any user, so it can never appear in
results), just not maximally clean. A full fix would mean threading an
exclusion list into `ingest.pipeline` itself, which felt like scope creep
for a cosmetic residual with zero leakage risk.

## Also found: the main index was stale on the node, unrelated to P5

Running `eval.run --index real` mid-session (a sanity check that the
enterprise-demo work hadn't touched the main index) returned
`nDCG@10=0.0000` — alarming until traced: `data/tantivy_index/` and
`data/registry.db` were simply empty/missing on the node (an artifact of
this same multi-session workflow, not something this P5 work did — the
enterprise work only ever touched `enterprise_tantivy_index_dir`/
`enterprise_registry_db_path`, confirmed by inspecting the actual paths
used). Ran `ingest.pipeline` fresh (`scanned=35 unchanged=0 added=35` —
confirming it had genuinely been empty, not just stale) and re-measured:
nDCG@10=0.8877, MRR=0.9107, recall@20=0.9048 — within the incremental-
rebuild variance band already documented in
`LOGBOOK_09022026_214005.md` (that logbook's own two independent fresh
builds landed at 0.8911 exactly; this run's 0.8877 is a similarly small,
already-understood drift, not a new regression). Noting this here for
continuity rather than treating it as newly discovered: node-side state
between sessions isn't durable by default, and re-verifying it before
relying on a "recorded" baseline is worth doing routinely, not just when
something looks wrong.

## Exit criteria — measured live, on sensalis-node

`tests/access/test_permission_denial.py`, run for real against
`data/enterprise_demo/` (Git connector → Postgres ACL + a fresh Tantivy
index → `PermissionAwareSearch`), 7 scenarios, all pass:

```
bob searching "Nightingale"  -> alice_private_notes NOT in results
alice searching "Kingfisher" -> bob_private_notes NOT in results
carol (unrelated 3rd user)   -> sees neither private document
alice/bob/carol searching "remote-work policy" -> public_policy IS in all three
bob searching "Project Falcon"   -> shared_project_plan IS in results (explicit grant)
carol searching "Project Falcon" -> shared_project_plan NOT in results (no grant)
alice searching "Nightingale"    -> alice_private_notes IS in results (owner)
```

Full suite on sensalis-node (Memgraph + Postgres both running): **162
passed, 1 skipped** (only the PDF test). Without either service (dev
laptop): **112 passed, 51 skipped** (29 `tests/kg/` + 21 `tests/access/` +
the PDF test) — confirmed both ways, same pattern established in P4.
