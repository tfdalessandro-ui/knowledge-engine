# Logbook — P2 exit criterion FAILS post-merge; root-caused a pre-existing FAISS/registry orphan gap

**2026-09-03, ~17:27 CEST** (`date -u` ~15:27, +2h)

Follow-up to `LOGBOOK_09032026_140900.md` (crawler scheduled, allowlist
grown 5->12, 7 new pages merged into the main corpus, 47 documents total).
Asked to re-check the P2 eval-harness margin after that merge. Found a
real regression below the exit criterion, and a separate, real, pre-existing
data-integrity bug uncovered while investigating a discrepancy between two
measurement paths. Both are recorded here in full.

## Part 1: the margin dropped below the 5% bar

`eval.run --index hybrid` (querying the live, persistent on-disk index)
and `pytest tests/eval/test_hybrid_vs_bm25.py` (the actual exit-criterion
test, which builds a completely fresh index in a temp dir from
`data/corpus/`) gave **two different answers**:

- Live on-disk index: nDCG@10 hybrid=0.8305 vs BM25=0.7924 -> **+4.81%**
  (my manual calc from the CLI harness)
- Fresh-built test index: nDCG@10 hybrid=0.7957 vs BM25=0.7924 -> **+0.4%**,
  test **FAILS** (`AssertionError: hybrid only improved nDCG@10 by 0.4%,
  below the 5% exit criterion`)

Both used the identical BM25-only score (0.7924, since Tantivy has no
orphan-style bug and both paths read the same corpus) -- the disagreement
was entirely in the hybrid number, meaning the vector side specifically.
`recall@20` matched closely between the two, meaning roughly the same
*documents* were being found either way -- the disagreement was in
*rank order* within top-10, which pointed at the vector index's internal
state rather than at what content is or isn't indexed.

## Part 2: root cause -- a pre-existing FAISS/registry orphan gap

Investigated rather than assumed the two numbers were just ordinary HNSW
build-to-build nondeterminism (a real, known property of approximate
nearest-neighbor graphs, and the first, cheaper explanation to check
against, but not the one that turned out to be true here).

**Found:** the live FAISS index physically contained **376 vectors**, but
`vectors.db` (the registry HybridIndex/`_vector_hits` uses to resolve a
FAISS-returned vector_id back to a doc_id/chunk_id) tracked only **341**
as live, with **0 rows marked `deleted=1`** -- meaning 35 vectors exist in
the FAISS graph with **no registry row at all**, not even a tombstoned
one. `HybridIndex._vector_hits()` silently `continue`s past any FAISS hit
whose vector_id isn't found in the registry (`src/eval/hybrid_index.py`),
so these orphans never directly appear in results -- but they DO consume
real slots out of the fixed `chunk_fanout` (default 100) candidate window
during FAISS's own top-k search, before that filtering happens. That
means every hybrid query was searching a graph where up to 35 of its
"neighbors" were always going to be discarded, effectively shrinking the
real candidate pool below what `chunk_fanout` was designed to guarantee.

**Confirmed this gap pre-dates today's session, not something today's
crawl/merge introduced:** this session's `ingest.pipeline` run added
`vectors_added=159` symmetrically to both faiss ntotal and the registry
count (159 chunks from the 7 new pages, added via the same code path to
both). Subtracting that from the post-run totals (376 faiss / 341
registry) gives the exact **pre-run** state: 217 faiss / 182 registry --
**the same 35-vector gap already existed** before this session touched
anything, i.e. it dates back to the 40-document state from an earlier
session.

**Checked whether the current code could produce this gap going
forward -- it can't, under normal operation:** read `run_ingest()`
(`src/ingest/pipeline.py`) directly. `vector_index.add(...)` and
`vector_registry.add_chunks(...)` are called back-to-back for the exact
same `(vector_ids, chunks)` pair, every single time, with no path where
one runs without the other for the same chunk set. So this specific
35-vector gap most likely predates the current code, or came from a
manual/debug script that touched the live `data/faiss_index/index.faiss`
directly outside the normal pipeline in an earlier session -- not
something this investigation could pin to an exact prior commit/session
without more historical log data than was available, and not worth
over-investigating further given the fix (compaction) is safe and the
forward-going code path is confirmed sound.

**A secondary finding, independent of the orphan gap's origin:** the
auto-compaction trigger (`vector_registry.tombstone_ratio() >
vector_compact_threshold`, default 0.2) can **never** catch this class of
bug. It's computed from the ratio of explicitly-tombstoned rows to total
rows -- a pure orphan (present in FAISS, absent from the registry
entirely) contributes to neither the numerator nor the denominator, so
the tombstone ratio stays exactly as if the orphans didn't exist. This
means compaction, as currently designed, only ever cleans up its own
documented tombstone-bloat case (P2's original known limitation, per
`src/ingest/index_faiss.py`) and has no mechanism to detect or fix a
FAISS/registry desync of this different kind. Worth a `KE_*` follow-up if
this project continues: a periodic sanity check comparing `faiss.ntotal`
against `len(registry.all_active())` and alerting/logging on any
mismatch, since nothing currently would surface this on its own.

## Part 3: forced compaction, confirmed live -- this was the actual cause

Backed up both files first (`data/faiss_index/index.faiss.bak_pre_forced_compact_20260903`,
`data/vectors.db.bak_pre_forced_compact_20260903`), then ran a standalone
script (`force_compact.py`, same logic as `run_ingest`'s own compaction
branch: `VectorIndex.rebuild(ids, vectors)` from `registry.all_active()`
only, re-embedding their stored text) against the **live** index -- asked
the user explicitly before running it, since it's a direct write to
production data outside the normal ingest path (the session's own
permission classifier also independently blocked the first attempt for
the same reason, correctly).

```
faiss ntotal BEFORE: 376
registry live count: 341
faiss ntotal AFTER:  341
```

Re-scored the live index immediately after:
```
=== Eval report (index: hybrid) ===
nDCG@10: 0.7948   MRR: 0.7997   recall@20: 0.9375
```
**This closed almost the entire gap** -- from 0.8305 down to 0.7948,
converging with the test's fresh-build number of 0.7957 (residual ~0.1%
difference, well within ordinary HNSW build-to-build variance, not a
further open question). Relative improvement on the now-compacted live
index: (0.7948-0.7924)/0.7924 = **+0.30%**, matching the test's +0.4%
closely. **The orphan vectors were the real, confirmed, root cause of the
discrepancy between the two measurement paths** -- not HNSW
nondeterminism, which was the cheaper first hypothesis and turned out to
be wrong (or at most a very minor residual contributor).

Restarted `knowledge-engine.service` afterward (PID changed
1181917 -> 1206068) so the live `/search` API picks up the compacted
index; verified `/health` returns `200 OK` post-restart.

## Part 4: the honest bottom line on the P2 exit criterion

**P2's exit criterion currently FAILS, confirmed two ways (the actual
pytest test, and the now-corrected live index): hybrid beats BM25-only by
roughly +0.3-0.4% nDCG@10, well under the 5% bar.** This is a real,
disclosed regression from the +6.0% measured right after the first P6
merge (`LOGBOOK_09032026_142903.md`), not a measurement artifact -- the
orphan-vector bug was a real confound in one of the two numbers being
compared, but resolving it did NOT rescue the exit criterion; if anything
it confirmed the fresh-build test's more pessimistic number was the
trustworthy one all along.

**Likely driver (not yet independently re-verified query-by-query the way
the first merge's regression was in Part 6 of `LOGBOOK_09032026_142903.md`):**
the same competing-content dynamic as before, now compounded a second
time -- this session's 7 newly crawled pages (Wikipedia articles on
Learning-to-rank, Knowledge graph, NER, LLMs, Vector databases) are
directly on-topic for several judgment-set queries and plausibly compete
for top-k slots on both sides of the BM25-vs-hybrid comparison again, the
same mechanism documented for the first 5-page merge. Not independently
re-confirmed this time query-by-query; flagged as the likely explanation,
not a proven one, to avoid repeating the earlier "P2 regressed" mistake
that later got corrected in `LOGBOOK_09032026_142903.md` Part 6 -- that
correction was about *which measurement was authoritative* (node vs
laptop), a different question than this session's *is 5% actually met at
all right now*, which both authoritative measurements now agree it isn't.

**What this means for the roadmap:** P2's README/roadmap status should be
updated to reflect this -- it can no longer honestly say "still passing"
at the current corpus size. This has NOT yet been updated in
README.md/HELP.md as of this logbook entry; that's the next step, along
with deciding (with the user, not unilaterally) whether to: (a) accept
the regression and document it as the current honest state, (b) revert
the 7-page allowlist expansion, or (c) grow the P0/P1 judgment set so the
comparison isn't so sensitive to a handful of competing high-relevance
crawled pages at this corpus's current small scale (28 judged queries).

## Why this belongs in the logbook in this much detail

This is exactly the kind of finding this project's own established
pattern says to write down in full rather than silently fix: a real,
reproducible bug (FAISS/registry desync) was found while investigating
what looked at first like it might just be approximation noise, confirmed
by a live before/after test rather than assumed, and the fix did NOT
produce the comfortable outcome (it did not rescue the P2 exit criterion
-- if anything it confirmed the worse number was correct). Reporting the
regression honestly, including that fixing the bug didn't fix the actual
metric, is the same discipline `LOGBOOK_09032026_142903.md` established
for this project and that discipline is what surfaces real problems
instead of papering over them with the more convenient number.
