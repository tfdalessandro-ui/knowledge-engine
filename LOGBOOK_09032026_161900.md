# Logbook — GA parameter tuning for P2 confirmed to overfit; not deployed

**2026-09-03, ~18:19 CEST** (`date -u` ~16:19, +2h)

Follow-up to `LOGBOOK_09032026_161500.md` (session paused mid-run for an
unplanned node power-off). The node came back online and the
cross-validation run had actually completed before/during the outage
(read from `ga_tune_hybrid_cv.log` on reconnect) -- recorded here in full,
per the standing instruction to always log findings.

## Recap: what was tried and why

`LOGBOOK_09032026_155830.md` left P2's exit criterion at -1.68%
(hybrid below BM25-only) after the judgment-set-growth attempt also
failed to fix it. Asked to try a genetic algorithm over `HybridIndex`'s
two exposed parameters (`rrf_k`, `chunk_fanout`) instead of touching the
corpus or judgments again.

**`ga_tune_hybrid.py`** (GA against the full 30-query judgment set,
read-only against the live compacted index): found `(rrf_k=1,
chunk_fanout=61)` scoring **+1.97%** vs. the default `(60, 100)`'s
**-1.68%** -- a real improvement, but flagged immediately, before doing
anything with it, as suspicious: `rrf_k=1` is a near-degenerate corner of
the RRF formula, and the GA was tuned and measured against the exact same
30 queries -- a textbook overfitting setup with no held-out data.

## The overfitting check: GA-tuned parameters generalize WORSE than the default

`ga_tune_hybrid_cv.py`: 5-fold cross-validation, ~6 held-out queries per
fold, GA re-run from scratch on each fold's other ~24 queries, then both
the fold's GA-selected genome and the fixed default scored on that fold's
held-out queries (never seen by that fold's GA search).

```
Fold  GA genome (from train)  train rel.   held-out: GA genome   held-out: default(60,100)
0     (61, 30)                 -0.81%       +0.13%                +2.04%
1     (120, 20)                -0.72%       -0.37%                +1.23%
2     (57, 129)                +3.08%      -18.09%               -18.09%
3     (177, 39)                -0.85%       +3.36%                +3.95%
4     (1, 52)                  +1.27%       +4.85%                +4.34%

Average TRAIN rel_improvement (GA, in-sample):     +0.39%
Average HELD-OUT rel_improvement (GA genome):      -2.03%
Average HELD-OUT rel_improvement (default 60,100): -1.31%
```

**Confirmed overfitting, two independent ways, not just asserted from the
averages:**
1. **No stable winner across folds** -- the 5 GA-selected genomes,
   `(61,30) (120,20) (57,129) (177,39) (1,52)`, are scattered across the
   entire search space with no consistent region of agreement. A genuine
   signal would produce similar winners across folds trained on
   overlapping data; this doesn't.
2. **The GA's picks underperform the untouched default on held-out data**
   in 3 of 5 folds, and the average held-out number for the GA
   (-2.03%) is worse than the default's own held-out average (-1.31%) --
   the opposite of what the full-set GA run appeared to show.

**A second, separate finding, not the main question but worth keeping:**
fold 2's held-out result was -18.09% for BOTH the GA genome and the
default -- identical, because that fold's 6 held-out queries happen to be
hard for this index regardless of RRF parameters. This is a real signal
that **the judgment set is currently too small to support reliable
held-out evaluation at all** (6-query folds have enormous variance,
visible directly in how wildly the per-fold numbers swing: -18% to +4.85%
for the exact same default parameters depending only on which 6 queries
landed in that fold). Any future tuning attempt on this project should
grow the judgment set substantially (well beyond the 30 queries reached
in the earlier session) before trusting held-out numbers from it.

## Decision: not deployed

The live `knowledge-engine.service` / `api/main.py` were never touched --
they still construct `HybridIndex` with the library defaults
(`rrf_k=60, chunk_fanout=100`), unchanged throughout this entire
investigation. **That stays the case.** The GA's full-set result
(+1.97%) is retracted as a viable fix, same as the judgment-set-growth
attempt before it -- both looked like progress in isolation and both
failed to hold up under a more rigorous check (node-vs-laptop
authoritative-environment check for the first merge; fresh-build vs
live-index check for the orphan bug; held-out cross-validation for this
one).

## Where P2 actually stands now, after three failed fix attempts

1. Accept-as-is (do nothing) -- the original fallback option.
2. Grow the judgment set -- tried, made the number worse and flipped its
   sign (`LOGBOOK_09032026_155830.md`).
3. GA-tune RRF/fanout parameters -- tried, the apparent improvement was
   confirmed to be overfitting via cross-validation (this entry).

**None of the three attempted fixes has actually closed the gap.** The
honest state remains what `LOGBOOK_09032026_152832.md` first established:
P2's exit criterion is not met at the current 47-document corpus size,
and every attempted fix so far has either not worked or made things
measurably worse under a more rigorous check. What's now additionally
clear is that the judgment set (30 queries) is too small to safely tune
anything against without a proper held-out methodology -- that's a
structural limitation of this demo-scale project, not something the next
attempt should route around with a smarter algorithm. Growing the
judgment set to a genuinely larger size (well past 30, with an actual
train/held-out split maintained going forward) would need to happen
before any further tuning attempt could be trusted.
