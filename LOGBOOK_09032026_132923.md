# Logbook — P7: Optional Small-LLM Answer Layer

**2026-09-03, ~13:29 CEST** (computed as `date -u -d "+2 hours"`, per the
tooling note in `LOGBOOK_09032026_000504.md`)

## Scope, per the roadmap artifact

P7 = "Optional small-LLM answer layer" — last on purpose, and skippable on
purpose: "the system must be fully usable without it." Deliverable:
extractive-answer generation over retrieved passages only, with every
generated claim traceable to a source chunk id. Tech choice: a quantized
3-7B instruct model via llama.cpp. Exit criterion: a sampled side-by-side
eval confirms answers cite the correct source passages. Named risk: "none
blocking — the retrieval system above it is already the complete product."

## What got built

- `src/answer/prompt.py` — `build_prompt()`: instructs the model to answer
  ONLY from the given passages, cite the exact `[chunk_id]` after every
  claim, never cite an unlisted chunk id, and say so plainly rather than
  guess when the passages don't contain an answer. The enforcement
  mechanism is the prompt plus the verification step below, not a
  fine-tuned model.
- `src/answer/citation.py` — `check_citations()`: extracts every `[...]`
  bracketed token from a generated answer and checks it against the set of
  chunk ids actually retrieved for that query, flagging anything else as
  invalid (hallucinated). This is the real traceability check the exit
  criterion needs — an instruction in a prompt is not a guarantee it was
  followed.
- `src/answer/model.py` — thin `llama_cpp.Llama` wrapper, lazy-loaded
  singleton (loading a multi-GB GGUF is the expensive part, done once per
  process).
- `src/answer/pipeline.py` — `AnswerEngine`: retrieves via the same
  `HybridIndex` P2 built, prompts, generates, validates citations. `main()`
  is a CLI (`python -m answer.pipeline "question"`) that exits with a clear
  message (not a crash) if the model isn't downloaded — P7 being optional
  is enforced in code, not just documentation.
- Tests: `tests/answer/test_citation.py`, `test_prompt.py` (pure Python,
  always run), `test_pipeline.py` (real model inference, gated behind
  `pytest.mark.requires_llm`, auto-skipped when the package/model aren't
  available — same pattern as Memgraph/PostgreSQL).

## Infrastructure: two real, disclosed constraints hit building this

1. **`llama-cpp-python` does not install on this Windows dev laptop at
   all.** The sdist bundles llama.cpp's web UI, which has paths deep enough
   to hit Windows' MAX_PATH limit: `No such file or directory` on a nested
   `.svelte` file under `vendor/llama.cpp/tools/ui/src/lib/components/...`.
   This is the same class of issue as an earlier, unrelated MAX_PATH
   problem on this same laptop (deep OneDrive-synced paths). Not worth
   fighting — P7 is execution-on-node-only, same as Memgraph/PostgreSQL.
   On sensalis-node (Ubuntu, gcc/g++ present), it builds from source via
   pip's own bundled cmake — no manual cmake install needed, ~5-10 minutes.

2. **Model choice, verified before committing to it:** Qwen2.5-3B-Instruct
   (Apache 2.0), Q4_K_M quantization from a well-known community quantizer
   (bartowski's HF repo) — confirmed the download URL resolves to a real
   file (`curl -I` returned a genuine signed CDN redirect, not a 404)
   before writing it into `HELP.md`. ~1.9GB, downloaded to
   `data/models/Qwen2.5-3B-Instruct-Q4_K_M.gguf` (gitignored — this repo
   does not commit or manage the model file).

## Exit criteria — measured live, on sensalis-node

Full test suite: `tests/answer/` — 14 tests, all pass (12 pure-Python +
2 real end-to-end LLM tests on a small synthetic fixture). Confirms the
mechanism works: no hallucinated citations on that fixture.

**The actual exit criterion — "sampled side-by-side eval confirms answers
cite the correct source passages" — needs human judgment, not just the
automated no-hallucination check**, so it was run as a genuine manual
review against the real P0-P6 corpus, 3 sampled queries:

| Query | Automated check (no hallucination) | Manual side-by-side (correct source per claim) | Time |
|---|---|---|---|
| "What is BM25?" | PASS (0 invalid) | **FAIL** — misattributed | 681.2s |
| "What does TF-IDF measure?" | PASS (0 invalid) | PASS | 543.4s |
| "What is HNSW used for?" | PASS (0 invalid) | PASS | 638.4s |

**Result: 3/3 pass the automated check, 2/3 pass genuine manual
verification.** This is a real, meaningful distinction the roadmap's exact
wording ("cite the correct source passages," not just "cite a real
passage") anticipates, and it would have been dishonest to report only the
automated 3/3 as if it satisfied the exit criterion.

**The one failure, verified against the exact source text (not just
skimmed):** for "What is BM25?", the model's answer strings together
sentences copied verbatim from three different chunks
(`doc01_bm25`, `doc34_kg_relations_demo`, `doc02_tfidf`), but its citation
brackets are shifted by one position — e.g. the sentence "BM25 remains a
strong, cheap baseline for keyword search..." (verbatim from
`doc01_bm25.txt`) is cited as `[doc34_kg_relations_demo::0]`, and "BM25
predates modern neural ranking methods, and TF-IDF predates BM25 itself."
(verbatim from `doc34_kg_relations_demo.txt`) is cited as
`[doc02_tfidf::0]`. Every one of those cited chunk ids WAS genuinely
retrieved for the query — so `check_citations()` correctly reports zero
invalid/hallucinated citations — but the citation attached to each specific
claim is the wrong one. This is a real limitation of a small 3B model at
this prompt design when several retrieved passages contain related,
similarly-worded content: it can correctly avoid inventing sources while
still misattributing which real source goes with which sentence.

**Not treating "2/3" as good enough to round up to "done," and not
spending further session time iterating on prompt engineering to chase a
better ratio** — each query costs 9-11 minutes of real wall-clock time on
this hardware, making rapid iteration impractical within this session, and
this is exactly the kind of imperfect-but-optional result the roadmap's
"no blocking risk" framing already anticipates for P7. The honest state is
recorded here rather than hidden or inflated.

## Measured latency (the roadmap's own justification for "optional")

681.2s / 543.4s / 638.4s per query (200 max output tokens, 5 retrieved
passages, Qwen2.5-3B-Instruct Q4_K_M, sensalis-node's 2-core Celeron, no
GPU). This is real, not a bug — a 3B-parameter model doing full-context
prefill plus token-by-token generation on 2 weak CPU cores is inherently
this slow. This is the concrete, measured version of the roadmap's own
stated reasoning for making this phase optional: the retrieval system
(P0-P6) already answers queries in tens of milliseconds and is the
complete, usable product; this layer trades ~10 minutes of CPU time for a
natural-language answer with citations on top of it.
