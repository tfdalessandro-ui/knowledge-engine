## What got built

- `src/ingest/parsers.py` — Docling (`DocumentConverter.convert().export_to_markdown()`)
  for PDF/DOCX/XLSX/PPTX/HTML/MD/CSV; dedicated readers for TXT (read as-is),
  JSON (pretty-printed), XML (text-node walk) — these three are flat data
  formats, not laid-out documents, so routing them through Docling's document
  model would be the wrong tool for the job.
- `src/ingest/chunking.py` — paragraph-split, word-count-as-token-proxy
  (documented explicitly: no real tokenizer, whitespace words), greedy
  packing to a 325-word target within the 250-400 band, 15% word-overlap
  carried into the next chunk, hard-split fallback for a single paragraph
  longer than max_tokens.
- `src/ingest/hashing.py` + `src/ingest/registry.py` — SHA-256 content hash
  per file, tracked in a SQLite table (`path`, `doc_id`, `content_hash`,
  `chunk_count`). This is what makes re-indexing incremental: the pipeline
  diffs against this table and only touches files whose hash changed.
- `src/ingest/index_tantivy.py` — Tantivy (`tantivy` PyPI bindings, v0.26)
  BM25 index. Schema: `doc_id`/`chunk_id` as raw (exact-match) text fields,
  `text` with the default tokenizer for BM25 search, `chunk_index` stored.
  Re-indexing a changed doc = `delete_documents("doc_id", old_doc_id)` (one
  call removes every chunk for that doc) + re-add its current chunks.
- `src/ingest/pipeline.py` — orchestrates scan → hash-diff → parse/chunk
  changed-or-new files only → index update → registry update → remove
  entries for deleted files. `IngestReport.touched()` = added+updated+removed,
  used directly by the incremental-rebuild test.
- `src/eval/real_index.py` — adapts the Tantivy index to the same
  `search(query, k) -> list[doc_id]` shape the P0 stub indices use (chunk
  hits collapsed to their doc_id, best rank kept), so `eval.run --index real`
  runs through the identical metric code as the stubs.
- `src/api/main.py` — FastAPI `/search?q=&k=` and `/health`, chunk-level
  results.
- `scripts/seed_corpus_p1.py` — 8 new corpus documents in md/html/csv/json/
  xml/docx/xlsx/pptx (generated via python-docx/openpyxl/python-pptx), each
  with real, on-topic content — not placeholder files. `data/judgments/judgments.json`
  grew from 63 to 79 pairs (28 queries) to cover them; still within the
  50-100 range, enforced by the existing `test_judgment_set_size` test.
- Test additions: `tests/ingest/test_chunking.py`, `test_parsers.py` (one
  test per format except PDF), `test_parsers_pdf.py` (network-gated, see
  below), `test_pipeline_incremental.py` (the incremental-rebuild exit
  criterion, asserted directly via `report.touched()`),
  `tests/eval/test_real_index_baseline.py` (the baseline-nDCG exit criterion,
  builds a throwaway real index in a temp dir and asserts+prints the score).

## Deviations flagged live, before proceeding

1. **PDF parsing needs network access, breaking P0's "fully offline" claim.**
   Verified directly: the first time Docling's PDF backend runs, it downloads
   OCR + layout-detection model weights from HuggingFace/ModelScope (~30MB+
   across several files, confirmed via captured log output). DOCX/XLSX/PPTX/
   HTML/MD/CSV do not trigger this — only PDF does. Decision: keep PDF
   parsing implemented (`parsers.py` supports it, per spec), but (a) don't
   include a `.pdf` file in the default seed corpus, so a default
   `ingest.pipeline` run stays offline, and (b) gate `test_parsers_pdf.py`
   behind `KE_ENABLE_PDF_TESTS=1` so the default `pytest -q` also stays
   offline (confirmed: 44 passed, 1 skipped, no network calls). Documented in
   both `requirements.txt` and `HELP.md`.

2. **CUDA/nvidia dependency pull on the node — caught mid-install, fixed
   before it did real damage.** Installing `pip install -r requirements.txt`
   fresh on sensalis-node (Linux) started downloading `nvidia-cudnn-cu13`
   (553MB), `nvidia-cusparselt-cu13` (170MB), `nvidia-nccl-cu13` (216MB),
   `nvidia-cublas` (423MB, mid-download when killed) — plain PyPI's default
   Linux `torch` wheel is CUDA-enabled and pulls these as declared
   dependencies, even though sensalis-node has no GPU and this entire project
   is explicitly CPU-first. Killed the install (`pkill -f 'pip install -r
   requirements'`), purged pip's cache (freed ~2GB, `/home` had dropped to 42GB
   free from a starting ~44-45GB), then fixed the install order: `pip install
   torch==2.14.0 torchvision==0.29.0 --index-url
   https://download.pytorch.org/whl/cpu` FIRST, confirmed `torch 2.14.0+cpu` /
   `torchvision 0.29.0+cpu` with `pip list | grep -i nvidia` empty, THEN `pip
   install -r requirements.txt` (which left the already-satisfied `+cpu`
   builds alone). Final venv: 1.8GB, zero nvidia packages. This ordering is
   now the documented install procedure in both `requirements.txt` (CRITICAL
   comment block) and `HELP.md` — matters again for CCX23 provisioning later,
   since CCX23 is Linux too and would hit the exact same default-PyPI trap.
   (The Windows laptop venv never had this problem — PyPI's Windows `torch`
   wheel has no CUDA extras by default — which is why this wasn't caught
   until the node install.)

judgment set's queries were authored closely matched to their target

topically distinct hand-written corpus) — not a tuned result, and not meant
to be one; P2's exit criterion is "hybrid beats this BM25 baseline by +5%
nDCG@10", so this number is the thing P2 has to beat, not a target to defend.

**Incremental re-index, proven end-to-end on the node:**
```
(fresh)                scanned=33 unchanged=0  added=33 updated=0 removed=0
(re-run, no changes)   scanned=33 unchanged=33 added=0  updated=0 removed=0
(edited doc01_bm25.txt) scanned=33 unchanged=32 added=0  updated=1 removed=0
```
`updated=1` with `unchanged=32` on the second edit-triggered run is the exit
criterion made concrete: one changed file touches exactly one document's
worth of index content, not a full rebuild. Reverted the test edit
afterward and re-ran ingest once more (`updated=1` again, back to original
content) so the node's corpus and index match the laptop's committed corpus.

Full test suite, node: `44 passed, 1 skipped in 7.02s` (PDF test correctly
skipped by default, per the flagged deviation above).
