## Scope, per the roadmap artifact (fetched at P1 start, same overall session)

P3 = "Usage capture & learning-to-rank": query log and result-selection
capture; once 500-1,000 interactions accumulate, a reranker trained on BM25
score, vector score, recency, and source type. Tech choice: LightGBM
LambdaMART (CPU-native, no GPU). Exit criterion: reranking the top-50
candidates improves nDCG@10 over RRF alone on held-out logged queries.
**Named risk in the roadmap itself: starting this before enough logged
signal exists.**

## Flagged before building anything

This system has zero real usage — no live traffic, no query logs, no
click/selection data anywhere. The roadmap's own stated risk directly
applies: training or evaluating a reranker against interactions that don't
exist would be dishonest. Asked the user how to handle this rather than
silently picking an approach. Answer: **build the query-log + selection
capture infrastructure now (the real P3 day-1 deliverable), wire it into
`/search`, and leave reranker training explicitly blocked/not-done until
real usage accumulates.** That's what got built.

## What got built

- `src/ingest/registry.py` (extended) — `source_type` and `ingested_at`
  columns (migration-safe `ALTER TABLE` for pre-P3 DBs), `get_by_doc_id()`.
  These are LTR features, not indexing-diff state.
- `src/ltr/query_log.py` — `QueryLog`: three tables (`queries`,
  `query_candidates`, `selections`). `log_query()` persists every search's
  ranked candidates with their BM25/vector/RRF scores + source
  type/recency; `log_selection()` records which one got picked.
  `training_rows()` returns query-grouped, binary-labeled rows ready for
  LightGBM's ranking objective (label=1 for the selected doc_id, 0 for every
  other candidate in that query).
- `src/eval/fusion.py` (extended) — `rrf_scores()` split out from
  `reciprocal_rank_fusion()` as shared core, so per-candidate RRF scores are
  available for logging, not just the final ordering.
- `src/eval/hybrid_index.py` (extended) — `HybridIndex.search_detailed()`:
  returns per-candidate BM25 score, vector score, RRF score, and text (not
  just the collapsed doc_id list `search()` returns, which stays unchanged
  for eval-harness compatibility).
- `src/ltr/features.py` — `row_to_features()` / `rows_to_dataset()`: turns
  logged rows into a fixed 5-column feature vector (bm25_score,
  vector_score, rrf_score, recency_days, source_type_code) and a
  LightGBM-ready `(X, y, group)` tuple.
- `src/ltr/train.py` — `train_reranker()`, gated: refuses to fit below
  `min_interactions` (config default 500) and returns a clear
  `TrainResult(trained=False, reason="blocked: N/500 ...")` instead.
- `src/ltr/rerank.py` — loads a trained model, reorders candidates by
  predicted relevance.
- `src/ltr/status.py` — CLI: `queries logged / selections logged / status:
  ELIGIBLE|BLOCKED (N/threshold)`.
- `src/api/main.py` (rewritten) — `/search` now uses
  `HybridIndex.search_detailed()`, logs every query via `QueryLog`, and
  returns a `query_id` in the response. New `POST /select` records a
  selection against that query_id.
- Tests: `test_query_log.py`, `test_features.py`, `test_train.py` (proves
  BOTH the real-threshold-blocked behavior AND, separately, that the
  LightGBM plumbing works against synthetic data), `test_rerank.py`,
  `tests/api/test_main.py` (end-to-end via FastAPI's `TestClient`).

## A real threading bug the tests caught, not a test-authoring mistake

`tests/api/test_main.py::test_select_records_an_interaction` — which makes
two HTTP requests in sequence, `/search` then `/select` — failed with:

```
sqlite3.ProgrammingError: SQLite objects created in a thread can only be
used in that same thread. The object was created in thread id 25660 and
this is thread id 11544.
```

Root cause, traced directly: FastAPI runs synchronous endpoint functions via
`run_in_threadpool`, and consecutive requests can land on different worker
threads. The API layer holds `QueryLog`/`DocumentRegistry`/`HybridIndex`
(which itself holds a `VectorRegistry`) as module-level singletons across
requests — so the `sqlite3.Connection` object, created in whichever thread
handled the *first* request that touched it, gets reused from a *different*
thread on a later request. `sqlite3.connect()` defaults to
`check_same_thread=True`, which raises exactly this error the moment that
happens. This is a real production bug, not a test artifact — any deployment
serving more than one request would eventually hit it.

Fixed at the root in all three SQLite-backed classes
(`ingest/registry.py`, `ingest/vector_registry.py`, `ltr/query_log.py`):
`sqlite3.connect(db_path, check_same_thread=False)` **plus an explicit
`threading.Lock()` wrapped around every method that touches the
connection**. `check_same_thread=False` alone only lifts the same-thread
*check* — it does not make a bare sqlite3 connection safe for actual
concurrent use from multiple threads at once (that's on the caller to
serialize, per Python's own sqlite3 docs); the lock is what makes this
correct under real concurrent load, not just past this one test's
sequential two-request pattern. Re-ran the full suite after the fix: 92
passed (up from 79 pre-P3), 1 skipped.
