# Logbook — P7 20-query citation-validation batch: quality review

**2026-09-08, ~13:35 CEST** (`date -u` ~11:35)

## Context

Step 5 (P7 citation validation expansion, 3 -> 20 samples) finished
overnight: `p7_batch_run.py` completed all 20/20 queries (last checked
mid-run at 14/20; log confirms `ALL DONE`, per-query times 1661s-4804s).
This entry reviews the actual answer quality of those 20 results, not
just completion.

## Finding 1 (minor, benign): citation-checker false positives

Aggregate citation stats across all 20 results:
```
total citations found: 483, valid: 468, invalid: 15
```
3 of 20 queries have >=1 "invalid" citation. Investigated each rather
than accepting the aggregate:

- **11 invalid citations, 1 query** ("first relevant result rank scoring
  for question answering"): all 11 are markdown hyperlink text fragments
  (`"machine learning"`, `"supervised"`, `"Chatbot"`, etc.) from raw,
  unstripped Wikipedia HTML the model quoted verbatim in its answer.
  `src/answer/citation.py`'s `_CITATION_PATTERN = r"\[([^\[\]]+)\]"`
  matches ANY bracketed text, so `[machine learning](url)` markdown link
  syntax gets misidentified as a citation marker. **This is a
  citation-checker bug, not a hallucination** -- the model didn't
  fabricate a source, the validator's regex is over-broad.
- **4 invalid citations, 2 queries** (`doc23_reciprocal_rank_fusion`,
  `doc13_python_venv` x3): genuine doc IDs that WERE in
  `retrieved_chunk_ids`, but emitted without the required `::chunk_idx`
  suffix (e.g. `[doc23_reciprocal_rank_fusion]` instead of
  `[doc23_reciprocal_rank_fusion::0]`). A real citation-formatting
  compliance miss by the model, but not a hallucinated source -- the
  correctly-suffixed form of the same doc also appears in the same
  answer in most cases.

**Zero actual hallucinated citations** (a chunk_id cited that was never
retrieved) found across all 20 samples.

## Finding 2 (significant, NOT previously surfaced): degenerate repetition in 12/20 answers

Scanned all 20 `answer_text` values for runs of 5+ consecutive identical
bracketed tokens. **12 of 20 (60%) show a severe repetition loop**,
typically after 1-3 genuinely correct sentences of answer, e.g.:
```
The roadmap has eight phases, P0 through P7. P0 and P5 are hard gates.
P0 builds the evaluation harness before anything it will measure exists,
and P5 requires permission-aware retrieval before any enterprise source
is indexed. [doc33_roadmap_overview::0] [doc33_roadmap_overview::0]
[doc33_roadmap_overview::0] ... (repeats ~140+ times) ... [doc
```
(cut off mid-token by `max_tokens=512`, confirming the repetition runs
all the way to the generation limit, not just a local stutter). Measured
where the repetition run starts vs. total answer length -- in the worst
cases the repeated tail is 60-82% of the entire answer's character count.
Affected queries: `a spreadsheet documenting benchmark latency results`,
`best metric when a user only needs one correct answer`,
`combining bm25 score vector score click history and freshness signals`,
`crawler responsibility is discovery not ranking`,
`document chunking for indexing`,
`highlighting matched phrases in full text search results`,
`layered proximity graph structure for nearest neighbor search`,
`merging lexical and semantic ranked result lists`,
`openapi documentation generated from type annotations`,
`python virtual environment versus the system python install`,
`roadmap phases and hard gates`,
`separating what gets indexed from how it gets ranked`.

**Root cause, read from source, not guessed**:
`src/answer/model.py`'s `generate()` calls llama.cpp with
`temperature=0.0` (pure greedy decoding, `Settings.llm_temperature`
default) and passes no `repeat_penalty` override at all. Once a small
3B instruct model (`Qwen2.5-3B-Instruct-Q4_K_M`) runs out of new content
to generate for a short factual answer, greedy decoding with no
repetition penalty is a well-known failure mode: it gets stuck
re-emitting the highest-probability next token (here, the citation
marker for the doc it just cited) until `max_tokens=512` cuts it off
mid-token.

**This was not visible in the original 3-query citation-validation set**
-- this is new information the 20-query expansion surfaced, consistent
with the whole point of Step 5's expansion (a 3-sample set is too small
to catch a failure mode this common). The underlying retrieval and the
first 1-3 sentences of each affected answer ARE genuinely correct and
well-grounded (confirmed by reading them directly) -- the defect is
purely in generation continuing past where it should stop, not in
retrieval or citation correctness of the good part.

**Not fixed in this pass** -- this was a quality-check request, not a
fix request. Flagging the fix for a follow-up: llama.cpp exposes
`repeat_penalty` (llama.cpp's own default is 1.1, but `Llama.__call__`
in this project's wrapper is called without setting it explicitly, so
it's worth confirming what the library's actual default resolves to)
and stop-sequence tuning could both help; a repeated-bracket-token
post-truncation heuristic (cut the answer at the first repeat) would
also make already-generated good answers usable without a model change.

## Overall P7 assessment (disclosed plainly, not softened)

- Retrieval + citation grounding: strong (0/483 hallucinated citations
  across 20 samples, citation-checker false-positive-adjusted).
- Answer generation: **60% of samples degrade into unusable repetition
  after a short correct start** -- this is a real, previously-hidden
  defect, not a minor polish issue. P7 remains an "optional, honest
  partial result" per its original framing (see prior LOGBOOK/git log
  entries), and this finding sharpens exactly what "partial" means here.
