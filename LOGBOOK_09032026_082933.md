## Scope, per the roadmap artifact

P6 = "Web crawl expansion": a vertical crawl of named, reviewed sources —
explicitly NOT general web crawling. Deliverable: robots.txt compliance,
per-domain rate limiting, canonicalization/dedup, and an explicit allowlist
with ToS review before any URL is fetched. Tech choice: reuses the P1
parsing & indexing pipeline. Exit criteria: allowlisted crawl completes
within a stated politeness budget; extracted pages pass through P1
ingestion unchanged. Named risk: "treat the list as the deliverable, not a
formality."

## A scoping call made and flagged: the roadmap's example domain doesn't fit this project

The roadmap's illustrative language ("an allowlist of OEM sites and trade
publications") is generic template text, not literal to this project — this
repo has no auto-parts/enterprise business context, so inventing fictitious
OEM sites to satisfy that phrasing would be worse than picking something
real and honestly justified. Instead built a small allowlist genuinely
on-topic for this project's own subject matter: 2 Wikipedia articles
(Okapi BM25, TF-IDF) plus one more (HNSW), SQLite's official FTS5 doc, and
Python's official sqlite3 stdlib doc — all directly relevant to the
project's own corpus content, not arbitrary.

Checked each candidate domain's actual robots.txt directly (`curl
https://<domain>/robots.txt`) before adding anything — not assumed
permissive. One candidate, `fastapi.tiangolo.com`, was deliberately NOT
added: its robots.txt uses an ambiguous, emerging "content signals" format
that defines terms like `search`/`ai-input`/`ai-train` but doesn't declare
an explicit yes/no value for any of them — a genuine gray area, and given
the roadmap's own "treat the list as the deliverable" warning, resolving
ambiguity by just not crawling it felt like the right call rather than
interpreting silence as permission.

## What got built

- `src/crawl/allowlist.py` — `ALLOWLIST`: 5 `AllowlistEntry` records, each
  with a `reason` (why this URL) and a `robots_checked` note (what was
  actually verified, with a date) — the list itself carries its own review
  evidence, not just URLs.
- `src/crawl/robots.py` — `RobotsChecker`, stdlib `urllib.robotparser` for
  the actual rule matching, but fetches robots.txt itself rather than using
  `RobotFileParser.read()` (see the bug below for why). RFC 9309-aware
  fallbacks: a 4xx/absent robots.txt is treated as unrestricted, a 5xx or
  network failure is treated cautiously (disallow), not the same as "no
  policy stated."
- `src/crawl/canonicalize.py` — strips tracking params (`utm_*`, `fbclid`,
  `gclid`...), normalizes scheme/host/trailing-slash/fragment, sorts
  remaining query params — so differently-formatted URLs to the same page
  dedup correctly.
- `src/crawl/rate_limiter.py` — `PerDomainRateLimiter`: never fetches two
  pages from the same domain faster than a configured minimum interval
  apart, independent of how many other domains are in flight.
- `src/crawl/fetcher.py` — `fetch_url()` via `httpx` (already a transitive
  dependency from FastAPI/starlette, no new package needed), with a
  declared, identifiable `USER_AGENT` naming the project and its repo.
- `src/crawl/pipeline.py` — `run_crawl()`: robots check → rate limit →
  fetch → canonicalize/dedup (via a small SQLite `CrawlState`, same
  incremental spirit as `ingest.pipeline`'s content-hash registry) → save
  HTML. `main()` then calls the SAME `ingest.pipeline.run_ingest()` every
  other corpus uses, unchanged, into a dedicated `data/web_tantivy_index/`
  (not the main index — same reasoning as P5's `enterprise_*` split: keep
  ungoverned crawled content out of the index the P1/P2 baseline numbers
  were recorded against).
- Tests: `tests/crawl/` — canonicalize, rate limiter, robots (against a
  local test HTTP server, not the real allowlist), allowlist structure, and
  the full crawl mechanism end to end. All run offline, always, no
  skip/gate needed (crawling doesn't depend on external service
  infrastructure the way Memgraph/Postgres do — it depends on live network
  access to arbitrary third-party sites, which is a different and worse
  thing to make the default test suite depend on, so the real allowlist
  crawl is verified manually/via the CLI and recorded here instead, the
  same split P0-P5 already use between "pytest proves the mechanism" and "a
  real run records the actual numbers").

## A real bug found by running the crawl for real, not by inspection

First real crawl attempt: `skipped_robots_disallowed=3` out of 5 URLs —
unexpected, since all 5 had been manually verified permitted via `curl`
minutes earlier. Traced it directly: `urllib.robotparser.RobotFileParser.read()`
fetches robots.txt using `urllib.request`'s bare default User-Agent
(`Python-urllib/x.y`), and Wikipedia returns **HTTP 403 Forbidden** for
that specific UA (confirmed with a raw `urllib.request.urlopen` call
reproducing the 403 directly). `read()` catches that error internally
without raising it to the caller, and sets `disallow_all = True` as its
conservative fallback — so all 3 Wikipedia URLs read as "robots.txt
disallows this" when the real cause was "the crawler couldn't even read
robots.txt anonymously." Fixed by fetching robots.txt manually with the
same declared `USER_AGENT` the real crawl uses (`crawl/fetcher.py`), then
feeding the text to the stdlib parser via `parser.parse()` instead of
`read()`. Re-verified: all 5 URLs correctly read as allowed after the fix.
While fixing this, also hardened the fallback behavior on non-200 robots.txt
responses to match RFC 9309 rather than treating every non-200 as
permissive (a 5xx server error means "policy unknown," not "no policy" —
these should not be treated the same).

## Environment notes from running this for real

- **Local Windows/OneDrive Tantivy-writer race, again** — the same
  transient failure already documented in earlier logbooks
  (`ValueError: An index writer was killed`) recurred when ingesting the
  crawled pages into a freshly-created index under the OneDrive-synced
  repo path. Isolated directly: copying a single crawled file to a
  non-OneDrive temp path and ingesting there succeeded immediately with no
  error. Not a new bug — the authoritative execution environment
  (sensalis-node, Linux, no OneDrive) doesn't have this problem, confirmed
  by running the real crawl+ingest there cleanly.
- **A self-inflicted "stale main index" pattern, now understood and fixed
  going forward.** The main `data/tantivy_index/` showed `nDCG@10=0.0000`
  on the node again this session (same symptom as during P5). Root cause,
  finally identified rather than just worked around again: this session's
  "ship to node" procedure excludes `data/tantivy_index/` etc. from the tar
  (correctly — those are local build artifacts, not source), but then does
  `rm -rf ~/work/knowledge_engine && mv new_dir ~/work/knowledge_engine` —
  which deletes the OLD directory (including its `data/tantivy_index/`)
  and the new one never had it, since it was excluded from the tar and only
  `.venv` gets explicitly copied over. Every "ship to a fresh directory"
  cycle this session has been silently wiping the main index; P4 and P5
  both hit this and it was rebuilt each time without tracing the actual
  cause. Rebuilt again here (`scanned=35 added=35`) and reconfirmed the
  baseline lands at nDCG@10=0.8877 — within the already-documented
  incremental-rebuild variance band from `LOGBOOK_09022026_214005.md`.
  **Going forward:** either re-run `ingest.pipeline` (and `kg.pipeline` if
  relevant) after every fresh-directory ship, or ship into the existing
  directory in place instead of the rm-rf-and-move pattern, when the goal
  is code updates rather than a truly clean environment test.
