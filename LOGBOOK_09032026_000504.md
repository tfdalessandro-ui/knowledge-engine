## What got built

- `src/ingest/embeddings.py` — BGE-Small (`BAAI/bge-small-en-v1.5`, 384-dim)
  via `sentence-transformers`, L2-normalized so FAISS inner-product search
  equals cosine similarity. `vector_id_for_chunk(chunk_id, text)` derives a
  stable int64 id from BOTH chunk_id and text content — see the bug below
  for why text has to be part of it.
- `src/ingest/index_faiss.py` — FAISS `IndexHNSWFlat` wrapped in
  `IndexIDMap2` (inner-product metric), persisted to a single file via
  `faiss.write_index`/`read_index`. `rebuild()` replaces contents entirely,
  used for compaction (below).
- `src/ingest/vector_registry.py` — SQLite metadata mapping vector_id ->
  (doc_id, chunk_id, text), with a `deleted` tombstone flag,
  `tombstone_ratio()`, and `hard_delete_tombstoned()`.
- `src/ingest/pipeline.py` (extended) — `run_ingest()` gained optional
  `vector_index_path`/`vector_registry_db` params (omit both = P1's original
  BM25-only behavior, keeps the P1 tests fast/offline/unchanged). When
  provided, every add/update also embeds the doc's chunks and updates the
  vector index; every update/removal tombstones the doc's old vector rows.
  Auto-compaction fires when `tombstone_ratio() > vector_compact_threshold`
  (default 0.2).
- `src/eval/fusion.py` — `reciprocal_rank_fusion(rankings, k=60)`,
  standard RRF formula, deterministic tie-break by first-seen order.
- `src/eval/hybrid_index.py` — `HybridIndex.search()`: BM25 chunk hits
  collapsed to a doc_id ranking, vector hits collapsed to a doc_id ranking
  (query embedded once, FAISS search, tombstone-filtered via the registry),
  the two rankings RRF-fused.
- `src/eval/run.py` — `--index hybrid` alongside the existing choices.
- `scripts/benchmark_p2.py` — uses the P0 generic `benchmark()` wrapper for
  both of P2's flagged measurements: embedding throughput (chunks/sec) and
  hybrid query p95 latency against a stated ceiling.
- Tests: `test_fusion.py`, `test_vector_registry.py`, `test_index_faiss.py`
  (synthetic vectors, no network), `test_embeddings.py` (real model, network
  on first run), `test_pipeline_vectors.py` (tombstone/compaction
  integration), `test_hybrid_vs_bm25.py` (the +5% exit criterion itself).

## A real, latent bug found by the tests, not by inspection

`test_editing_a_file_tombstones_old_vectors` and
`test_compaction_fires_above_threshold` both failed on first run, and the
failure was real, not a test-authoring mistake. Root cause: my first version
of `vector_id_for_chunk(chunk_id)` hashed only `chunk_id` (i.e., `doc_id` +
position). For a doc whose chunk count doesn't change across an edit (the
common case for a short document — one chunk before, one chunk after), the
new chunk's `chunk_id` is identical to the old one (`"beta::0"` both times),
so it hashed to the **same vector_id**. The pipeline's own sequence —
tombstone the doc's old rows, then `add_chunks()` — used
`INSERT OR REPLACE` on that same vector_id, which silently **resurrected
the just-tombstoned row** (reset `deleted` back to 0) instead of adding a
genuinely new one. Worse: the *old, stale* vector was still physically
sitting in the FAISS HNSW graph the whole time (HNSW can't `remove_ids`,
confirmed directly against faiss 1.15.0 — `RuntimeError: remove_ids not
implemented for this type of index`), so it would have stayed there forever,
uncounted by the tombstone-ratio compaction trigger, silently degrading
search quality with a duplicate stale-content vector under a live id.

Fix: `vector_id_for_chunk` now hashes `chunk_id` AND the chunk's text
content together. Any content change at the same position now gets a
genuinely fresh id, so the tombstone sticks and the stale FAISS entry is
correctly counted toward compaction. Re-ran the full suite after the fix:
70 passed (up from 44 in P1 + P0's original count), 1 skipped.

## Exit criteria — measured, on both laptop and sensalis-node

Fresh full ingest (`vectors_added=33`, all 33 documents/chunks, no PDF in
the default corpus per the P1 network-dependency decision):

| | BM25-only (`--index real`) | Hybrid (`--index hybrid`) |
|---|---|---|
| nDCG@10 | 0.8912 | 0.9502 |
| MRR | 0.9286 | 0.9821 |
| recall@20 | 0.9048 | 0.9732 |

**Relative nDCG@10 improvement: +6.6%** — clears the +5% exit criterion with
real margin, not a coin-flip pass. Identical numbers measured independently
on the laptop (Windows, sanity check) and on sensalis-node (the actual
execution environment) — full agreement.

**Query latency (hybrid, sensalis-node):** p50=63.6ms, p95=66.1ms.
**Stated ceiling: 500ms p95** (`QUERY_P95_CEILING_MS` in
`scripts/benchmark_p2.py`) — chosen as a reasonable interactive-search bound
for CPU-only hardware; comfortably passed (66ms vs. 500ms).

**Embedding throughput at ingest time (sensalis-node, the roadmap's flagged
risk):** ~6.6 chunks/sec, measured with a batch of 15 real corpus chunks
over 20 iterations after warming up the model. This is genuinely slow — a
2-core Celeron running a 33M-parameter transformer, no way around it without
better hardware or a smaller/quantized embedding model (out of scope for
P2). Worth carrying into future ingest-scale planning: a corpus of, say,
10,000 chunks would take ~25 minutes of embedding time alone on this node.

**A benchmarking mistake caught mid-measurement, worth recording:** my first
run of `scripts/benchmark_p2.py` reported embedding p95 latency of
**23,676ms** (on the laptop) — wildly inconsistent with a ~500ms median.
Traced it directly rather than assuming noise: the model is a lazy-loaded
singleton, and its ~15s one-time load cost was landing inside iteration 1 of
the timed `benchmark()` loop, since I hadn't called `embed_texts()` once to
warm it up first. Fixed by adding an explicit warm-up call before the timed
loop (standard benchmarking practice — should have done this from the
start). Even after the fix, the *laptop* run still showed occasional
multi-second outliers (p95=4254ms against a p50=568ms) — traced this too:
per-iteration timing showed all 15 raw iterations landing in a tight
450-650ms band with zero outliers, so the outliers in the wrapped
`benchmark()` run were something in the Windows environment (background AV
scan, OS scheduling — this laptop is dev-only, not the measurement
environment per the established repo/execution split). The **node** run
(the authoritative one) showed no such outliers: p50=2261.6ms,
p95=2716.7ms, max=3631.9ms for the same batch — normal variance, no
pathological spike. This is why the reported exit-criterion numbers above
are the node's, not the laptop's.

## Documentation gotcha found and fixed: my own "CEST" timestamps were UTC

While naming this file, discovered that `TZ="Europe/Rome" date` has been
silently falling back to plain UTC all session — this Git Bash environment
has no `/usr/share/zoneinfo/Europe/Rome` (`ls` confirms: no such file).
Setting an unrecognized `TZ` value doesn't error, it just no-ops to UTC,
labeled `GMT` in the output. Checked directly: at 2026-09-02 22:04:43 UTC,
the "CEST" command printed the same UTC clock time verbatim (`2026-09-02
22:04:43 GMT`), while true CEST at that moment was already **2026-09-03
00:04:43** — a full 2-hour-and-almost-a-calendar-day discrepancy. This
means every earlier timestamped logbook filename this session
(`LOGBOOK_09022026_173751.md`, `_175124.md`, `_214005.md`) is actually
labeled in UTC, not CEST as the house convention and [[feedback-timezone-cest]]
memory both require — though their *content* (prose mentions of "CEST")
inherited the same wrong computation, so they're internally consistent with
each other, just not correct relative to real CEST. Not renaming those
files retroactively (they're already committed/pushed, and renaming would
break nothing referencing them, but there's no value in it either — the
drift is now documented here). **Fixed going forward:** compute CEST as
`date -u -d "+2 hours" ...` instead of relying on `TZ=Europe/Rome`, since
this environment's tzdata is incomplete. This file's own timestamp
(`09032026_000504`) was computed the corrected way.
