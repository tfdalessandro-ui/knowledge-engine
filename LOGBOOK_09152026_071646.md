# Logbook — Weighted fusion was dead config; recovered a lost module, wired it up, fixed a real Sensalis ranking bug

**2026-09-15.** Started from a Sensalis-side task (a separate pricing-engine clone tested against real
Sensalis parts data — see that project's own notes) that surfaced a concrete symptom: an exact
part-code match sometimes ranked below a weaker but "consistent" document, and in one case didn't
appear in the top 5 at all. Traced the root cause back to this engine's own retrieval core, fixed it
here, then re-verified this project's own live service and Step 9 benchmark with the fix applied.

## Root cause

`HybridIndex` (`src/eval/hybrid_index.py`) only ever implemented Reciprocal Rank Fusion — rank-only,
deliberately blind to score magnitude. `Settings.hybrid_fusion_mode` ("weighted") and `hybrid_alpha`
(0.535) — the values `LOGBOOK_09042026_060353.md` documents as GA-tuned across two rounds of
cross-validation and found to beat RRF — existed in config the whole time but were **never actually
passed to `HybridIndex`**. `api/main.py`'s `_get_index()` built `HybridIndex(tantivy_dir, faiss_path,
vector_registry_db)` with no other kwargs at all, so the live service always ran plain RRF with
`rrf_k` defaulted to 60 (not the tuned `rrf_k=1`), regardless of what Settings said. `eval/run.py`'s
`build_index("hybrid", ...)` had the same gap.

RRF gives identical credit to "barely rank 1" and "overwhelmingly rank 1" — exactly the failure mode
behind the Sensalis symptom: an exact-code match can dominate BM25 by a huge margin and still only
count as "rank 1" once fused with a vector ranking that doesn't agree, letting a mediocre-but-present
document win on aggregate rank.

## A second, unrelated thing found along the way: the fix module itself was already lost

`src/eval/weighted_fusion.py` — the actual min-max-normalize + `alpha * bm25 + (1-alpha) * vector`
implementation the 2026-09-04 logbook describes as "a real, permanent addition to the codebase,"
unit-tested with 7 passing tests — **did not exist anywhere**: not in git (zero history, confirmed via
the GitHub API), not on the live node checkout. Recovered it from
`~/work/knowledge_engine_pretar_backup_20260914/` — the pre-migration tar-ship snapshot kept as a
safety net during 2026-09-14's git-clone migration. It had never been committed, so when that
migration swapped the live directory for a fresh `git clone`, this file (source code, not runtime
data) silently didn't come along — a real regression introduced by that migration, despite the
runtime-data resync being done carefully. All 7 of its original unit tests still pass unmodified.

## What was actually changed

- Restored `src/eval/weighted_fusion.py` + `tests/eval/test_weighted_fusion.py` verbatim.
- `HybridIndex.__init__` gained `fusion_mode` ("rrf" | "weighted") and `alpha` parameters.
  `search()`/`search_detailed()` branch on `fusion_mode`; the RRF path is untouched, byte-identical
  behavior to before when `fusion_mode="rrf"`.
- `api/main.py`'s `_get_index()` now passes `chunk_fanout`, `rrf_k`, `fusion_mode`, and `alpha` from
  `Settings` — the config was already correct, it just needed to actually reach the object it
  configures.
- `eval/run.py`'s `build_index("hybrid", ...)` gets the same wiring, so offline eval now matches what
  the live service actually does.
- Applied identically to the Sensalis pricing-engine clone (a separate project, not this repo) and to
  this repo, and confirmed on both.

## Verification

Direct in-process check that the two fusion modes genuinely differ (not a no-op branch):
```
query: "what is bm25 ranking algorithm"
RRF:      [..., 'https_sqlite_org_fts5_html_8acf991e', 'https_..._Learning_to_rank_...', ...]
Weighted: [..., 'https_..._Learning_to_rank_...', 'https_sqlite_org_fts5_html_8acf991e', ...]
SAME: False
```

Restarted `knowledge-engine.service` (fresh PID, confirmed via `systemctl status`), re-ran the full
`pytest -q` suite: **2 failures, both real and neither caused by this change** —
`test_judgment_set_size` asserts a stale `50 <= total <= 100` bound against a judgment set that's been
246 rows for several days (pre-existing, unrelated — a `TODO.md` follow-up now); and
`test_hybrid_vs_bm25.py::test_hybrid_beats_bm25_only_by_5_percent_ndcg10` shows hybrid *underperforming*
BM25-only by -2.9% on its own fixture, which disagrees with the live 126-query benchmark below and
hasn't been reconciled — flagged as open, not resolved.

Re-ran Step 9's comparative benchmark against the restarted live service:

| | Before (dead config, plain RRF) | After (weighted fusion, live) |
|---|---|---|
| This engine, full 126-query set | nDCG@10=0.9278 / MRR=0.9513 / recall@20=0.9696 | **identical, bit-for-bit** |
| Latency (p50 / p95) | 264.6ms / 578.5ms | **95.6ms / 122.9ms** |

The identical relevance number isn't a sign the fix silently didn't apply (the direct comparison above
proves it did) — nDCG@10/MRR/recall@20 only score judged positions, and the rank swaps this fix causes
here happen to be among documents with equal (often zero) judged relevance, so the ranking changes
without moving these particular aggregate metrics. Net effect on this corpus: neutral, as measured.
Net effect on the Sensalis clone's exact part-code lookup task (a different corpus, a different query
pattern): **10/15 correct top-1 -> 15/15**, including one case that previously didn't appear in the
top 5 at all. Same code change, task-dependent payoff — worth remembering rather than either crowning
it a universal win or dismissing it as a no-op because one benchmark didn't move.

The engine also got measurably faster (p50 264.6ms -> 95.6ms) for reasons not yet confirmed causally —
reported as observed, not claimed as an effect of this fix, since the two changed at the same time and
weren't isolated from each other.
