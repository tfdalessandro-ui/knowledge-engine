**2026-09-03, ~17:58 CEST** (`date -u` ~15:58, +2h)

Follow-up to `LOGBOOK_09032026_152832.md`, which found P2's exit criterion
genuinely failing (+0.4% nDCG@10, well under the 5% bar) after the second
crawl merge, and suggested growing the judgment set as the honest fix
(rather than reverting the crawl or loosening the threshold), reasoning
that the 28-query P0/P1 judgment set hadn't grown alongside the corpus
while the corpus grew specifically in the topic areas those judgments
cover. **That reasoning turned out to be wrong, or at least incomplete —
recorded here in full per the user's explicit instruction to always log
findings, not just report them in chat.**

## Result: the exit criterion is now WORSE, not fixed

```
=== Eval report (index: real, i.e. BM25-only) ===
queries judged : 30
nDCG@10     : 0.8477   MRR: 0.9067   recall@20: 0.8722

=== Eval report (index: hybrid) ===
queries judged : 30
nDCG@10     : 0.8335   MRR: 0.8520   recall@20: 0.9389
```

**Relative improvement: (0.8335 - 0.8477) / 0.8477 = -1.68%.** Hybrid now
scores *below* BM25-only, not just under the +5% bar. Confirmed via the
actual pytest exit-criterion test too (fresh-built indices, the
authoritative measurement path): still `xfail` (lowercase `x` = expected
failure, not an unexpected pass) -- `test_harness.py`'s judgment-set-size
test passed cleanly against the new 94/30 counts, so the growth itself was
structurally valid, it just didn't produce the hoped-for result.

## Why the hypothesis was wrong -- a real, disclosed miss, not glossed over

The reasoning in the prior logbook was: the judgment set wasn't crediting
the crawled pages' real relevance, so both scores were being measured
against an incomplete relevance signal, and fixing that would let the
already-narrow-but-real hybrid advantage show through cleanly. **What
actually happened is closer to the opposite for several of these
queries:** the newly-judged crawled Wikipedia pages are long, dense,
keyword-rich pages that BM25's exact term-frequency scoring rewards very
strongly and directly (e.g. `Okapi_BM25`'s wiki page literally contains
the phrase "Okapi BM25" and "ranking function" repeatedly) -- while the
hybrid layer's RRF fusion, by design, blends in vector-similarity results
that don't privilege exact term match the same way, and for these
specific well-matched literal queries, that blending pulled the fused
top-10 slightly further from the newly-added ground truth than BM25 alone
already was. This is a real property of RRF on this judgment set's current
shape (a handful of "obvious keyword match" queries now dominating the
average), not a bug in the fusion code or the grading -- but it is the
opposite of what growing the judgment set was expected to do, and that
gap between hypothesis and result is the actual finding worth keeping,
not the fact that a fix was attempted.

**Not yet done, and not assumed:** whether -1.68% itself is stable, or
whether it would move again with still more judgment coverage (e.g. the
skipped `wal.html`, or judging more of the *existing* 40 non-crawled docs
against the same queries more thoroughly) hasn't been tested. This result
should be read as "the first hypothesis for fixing P2 didn't work and
made the measured gap directionally worse," not as a final verdict on
whether hybrid retrieval is sound for this project -- P2's original
+6.6% result on the untouched 35-doc corpus is still real and still
stands as evidence the mechanism works; what's now clearly true is that
it's fragile to exactly which documents and judgments this small-scale
demo corpus happens to contain.

## Correction to the prior logbook's proposed fix

`LOGBOOK_09032026_152832.md` said: "Growing the judgment set to match the
corpus's current breadth ... would be the honest fix, not reverting the
crawl or arguing the threshold down." **That specific claim is now
retracted as stated** -- growing the judgment set was tried, in good
faith, and it did not fix the criterion; it's not yet clear it CAN be
fixed by judgment-set growth alone at this corpus's current small scale
(47 docs, now 30 judged queries). The three original options from that
logbook (accept as-is, revert the crawl, or grow the judgment set) turned
out not to be mutually exclusive or a menu where one clearly "wins" --
growing the judgment set was attempted and the honest result is simply a
different, still-failing number, which is itself new information, not a
dead end. The `xfail(strict=True)` reason string on
`tests/eval/test_hybrid_vs_bm25.py` still says "+0.4%" from before this
session's judgment-set growth -- **this is now stale and needs updating**
to the new measured number and this session's finding, which is the next
step, not yet done as of this entry.
