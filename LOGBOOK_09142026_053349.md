# Logbook — CX23 doc-discovery parity benchmark (Step 8)

**2026-09-13 18:03 UTC → 2026-09-14 04:18 UTC.** Requested as a benchmarking test:
feed this project's own Step 8 on-demand discovery pipeline (`src/discovery/pipeline.run_discovery`)
the SAME 30 keyword queries that Sensalis' production crawler (`/root/doc_source_discovery.py` on
CX23) issues, run entirely on sensalis-node, read-only w.r.t. CX23 — no code or config on CX23
touched, no merge of the two projects.

## Query set (verified live, not assumed)

Pulled directly from CX23 at run time: `/root/lectura_taxonomy.json` (40 brands, first-40 slice) x
`DOC_INTENT` (8 EU-language intent phrases, e.g. "service manual pdf" / "catalogo ricambi pdf" /
"Ersatzteilkatalog pdf"), interleaved brand x (lang, intent), capped at `DOC_MAX=30`. Exact 30
queries preserved in `data/benchmark_cx23_queries.txt` (this repo).

Deliberately NOT changed to force parity: Step 8's own hard per-query cap
(`MAX_URLS_PER_TRIGGER=3`) was left in place rather than raised to match CX23's pooled
`DOC_CAND_MAX=40`-across-30-queries. Loosening a safety guardrail just to chase a bigger number
would defeat the point of the guardrail.

## Run 1 — crashed at 14/30, no results file

Launched via bare `nohup ... &` over an SSH exec. Died silently after query 13 (mid-fetch on
query 14, "Bronto Skylift katalog części pdf") — no Python traceback, no OOM in `dmesg`. Best
supported explanation (not fully confirmed): the SSH session that spawned it (`journalctl -u
systemd-logind` shows session 13384 open 18:03→19:37) was torn down and took the orphaned
`nohup` child with it — `nohup` blocks `SIGHUP`, not a systemd session-scope kill. Queries 1-13's
work was NOT lost (already fetched+ingested into the discovery index; provenance rows exist), just
the run's own results file was never written since the script only wrote it at the very end.

Fix applied for run 2: (1) launched via `systemd-run --user --collect`, tying the process to the
persistent `user@1000.service` manager (confirmed `Linger=yes`) instead of an SSH session scope;
(2) patched `scripts/benchmark_cx23_discovery.py` to flush each query's result to a `.jsonl`
immediately (append+flush per row) instead of only writing a summary `.json` at the end, so a
second crash couldn't lose completed work again.

## Run 2 — remaining 17 queries (14-30), completed clean

`ke-benchmark-part2.service` (transient, `--collect`), started 19:39:32 UTC, ran 8h39m unattended,
self-collected on exit — no crash. All 17/17 completed, `data/benchmark_cx23_discovery_results_part2.jsonl`
authoritative.

## Combined results (30/30 queries)

- **90/90 documents fetched** (exactly `3 x 30` — the per-query hard cap was hit on literally every
  query; never candidate-starved by the search backend).
- Robots-disallowed: 1 (`Landini catalogo ricambi pdf`).
- Blocklist-skipped: 0.
- Fetch/parse errors: 6 (Manitou, Snorkel, Dinolift, Multitel x2, Valtra) — non-fatal, pipeline
  continued past each.
- **Total pipeline processing time: ~10h9m** (part 1: 5,440s / part 2: 31,112s), almost entirely
  RapidOCR on scanned/image PDFs (this node has no GPU, 2 Celeron cores). Per-query latency ranged
  2.2s to 12,681s (3.5h, `New Holland catalogue pièces détachées pdf` — a scanned PDF). CX23's own
  `doc_source_discovery.py` does NOT OCR anything (regex PN-density scan over already-fetched
  text/HTML only) — this is a genuine behavioral difference between the two crawlers' designs, not
  a defect in either. A bulk keyword sweep like this one, run again, would need OCR disabled or a
  multi-hour tail accepted per scanned-PDF hit.

## Side finding on CX23 (read-only, not investigated further — flagged, not fixed)

Checked CX23's own `doc_sources.db` + `doc_source_discovery.log` for comparison:
- `doc_sources.db` has **not gained a new row since 2026-08-31** (14 days stale as of this run),
  despite the `DOC_SOURCE_DISC` cron firing daily at 06:00 UTC.
- 13 of the last 43 logged runs end in `SearXNG + Serper both unavailable — stopping` -> `0 new
  candidate domains`, including the 2026-09-13 06:00 run.
- SearXNG itself was confirmed reachable from CX23 at benchmark time (`curl` -> `200`), so this
  isn't the search backend being down right now specifically — root cause not chased (out of this
  benchmark's scope).

**Net:** on the identical 30 queries, same day, same underlying SearXNG instance, this project's
Step 8 discovery found real fetchable candidates for all 30 (90 documents); CX23's production
crawler, on its normal schedule, found 0 new candidates and hasn't added anything in two weeks.
Reported as measured, not as a verdict on which system is "better" — CX23's failure mode is a
separate, unlinked problem, and Step 8's OCR tail is a real cost this comparison doesn't show CX23
paying.
